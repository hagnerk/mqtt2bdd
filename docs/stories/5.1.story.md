# Story 5.1: Stop Retrying Writes the Database Can Never Accept

## Status

Ready for Review

## Story

**As an** operator,
**I want** a message the database can never store to be discarded and logged instead of retried forever,
**so that** one bad payload cannot stop every other message from being persisted.

## Acceptance Criteria

> **ACs 1–12 are copied verbatim from Epic 5 in `docs/prd.md:892-911`.** None is reworded and none is added. Where an AC leaves a detail open, the answer is recorded in Dev Notes → SM Clarifications, with its source. Release target: **v1.0.1**, together with Story 5.2, which must merge after this one.

1. Write errors are classified inside `internal/database` as either *permanent* or *transient*. The classification is exposed to callers as a sentinel error matchable with `errors.Is` (for example `database.ErrRejected`), so `cmd/mqtt2bdd` never imports `pgconn` or reasons about SQLSTATE codes
2. An error is permanent if and only if it is a `*pgconn.PgError` (found with `errors.As`, so wrapping does not hide it) whose SQLSTATE class is `22`, `23` or `54`. Every other error is transient, including non-PostgreSQL errors, context deadlines, and SQLSTATE classes `08`, `40`, `42`, `53`, `57`, `58` and `XX`
3. Before any database round-trip, a payload that fails `json.Valid` is rejected locally with the same sentinel, without contacting the database
4. A zero-length payload (MQTT's way of clearing a retained message) is skipped before any round-trip: logged at DEBUG with `event=write_skipped` and `reason=empty_payload`, not counted as rejected, not treated as an error by the caller
5. When the error is permanent, `insertWithRetry` returns immediately — no 10-second wait — on both the steady-state path and the shutdown drain path, and the writer moves on to the next buffered message
6. A rejection is logged once, at ERROR, with `event=write_rejected`, `operation=insert`, `topic`, `payload_size`, `duration_us`, `reason` (`invalid_json` for a local rejection, `sqlstate` for a server one), `sqlstate` (server rejections only) and `error`. The payload body is never logged. `write_failure` keeps meaning "this write will be retried" and is no longer emitted for rejections
7. A server-side rejection proves the database answered, so it leaves the client connected: `connected` is set to `true`, never `false`. `lastWriteAt` and `writeCount` are not updated, because nothing was written
8. The database client exposes a monotonic rejection counter, and the `health_check` entry gains a `rejected_last_interval` field computed like `processed_last_interval`
9. Unit tests cover the classification with synthetic `*pgconn.PgError` values — at least `22P05`, `22P02`, `22021`, `22003`, `23502` and `54001` as permanent, and `08006`, `40P01`, `42501`, `42P01`, `53100`, `57P01` and `XX000` as transient — plus a wrapped `PgError`, a plain error and `context.DeadlineExceeded`
10. An integration test publishes, in this order, a non-JSON payload, a payload PostgreSQL rejects server-side (`{"v":1e1000000}`, which passes `json.Valid` and keeps failing after Story 5.2), an empty payload, and a valid payload. The valid row is stored well within the 10-second retry interval, the first three are absent, and two `write_rejected` entries are logged
11. `docs/architecture/error-handling-strategy.md`, `docs/architecture/logging-standards.md` and the README's troubleshooting and data-loss sections describe the new behaviour
12. Verification passes through the containerized toolchain from `dev/` — `gofmt -l .`, `go vet ./...`, `staticcheck ./...`, `go test ./...` — and `./test/run-integration-tests.sh` passes from the repository root

## Dev Notes

### Context: why this story exists

v1.0.0 stalled in production on `zigbee2mqtt/bridge/definitions` (283 KB, retained). PostgreSQL refused it with SQLSTATE `22P05` (` ` escape), `insertWithRetry` retried it every 10 seconds forever, `dbWriterLoop` — the buffer's only consumer — never moved on, the 1,000-slot buffer filled, and reception blocked. Because the message is retained, a restart reproduced the stall at once. `InsertMessage` also set `connected=false`, so the health entry reported `db_status=disconnected` while the database was answering. [Source: docs/sprint-change-proposals/2026-09-17-write-pipeline-stall.md#1-identified-issue-summary]

The architecture always defined a *Data Integrity (Log and Skip)* category; Stories 1.8, 1.9 and 2.3 implemented only the transient one. This story implements the classification and the rejection. Story 5.2 adds the repair of what can be repaired; Story 5.3 adds topic exclusion. [Source: docs/prd.md#epic-5-write-pipeline-hardening]

**Compatibility (Epic 5):** no schema change, no new Go dependency, and a valid payload is written exactly as today — same SQL, same retry behaviour on outages, same log entries. Rollback is `git revert`, which restores the stall. [Source: docs/prd.md → Epic 5 → Epic Context]

### Write Error Classification

| SQLSTATE class | Meaning | Classification | Reason |
|----------------|---------|----------------|--------|
| `22` | Data exception | Permanent | The value is invalid for the column: `22P05` (` `), `22P02` (invalid JSON, unpaired surrogate), `22021` (invalid UTF-8), `22003` (number out of `numeric` range) |
| `23` | Integrity constraint violation | Permanent | `23502` (NULL payload). `23505` never surfaces, because `ON CONFLICT DO NOTHING` absorbs duplicates |
| `54` | Program limit exceeded | Permanent | `54001` (nesting depth), `54000` (`jsonb` size) |
| `08`, `40`, `53`, `57`, `58`, `XX` | Connection, transaction conflict, resources, operator intervention, system, internal | Transient | They describe the environment, which recovers |
| `42` | Syntax error or access rule violation | Transient | Hits every message identically and an operator can fix it (a missing `GRANT` happened on 2026-09-17). Waiting keeps the buffered messages |
| n/a | Not a `*pgconn.PgError` (network error, context deadline) | Transient | No answer came from the database |

Reference shape from the architecture (adapt, do not copy blindly — see C7):

```go
var ErrRejected = errors.New("message rejected by database")

func isPermanent(err error) bool {
    var pgErr *pgconn.PgError
    if !errors.As(err, &pgErr) {
        return false
    }
    switch pgErr.Code[:2] {
    case "22", "23", "54":
        return true
    }
    return false
}

// cmd/mqtt2bdd — insertWithRetry
if err == nil || errors.Is(err, database.ErrRejected) {
    return // stored, or never storable: either way the message leaves the buffer now
}
```

[Source: docs/architecture/error-handling-strategy.md#3-runtime-errors---data-integrity-log-and-skip]

What the probe established (PostgreSQL 15.17, `pgx/v5` v5.7.2, `JSONB NOT NULL`): `json.Valid` is a useful local pre-check but not sufficient — ` `, unpaired surrogates, raw invalid UTF-8 and numeric overflow all pass it and fail on the server. `{"v":1e1000000}` passes `json.Valid` and fails with `22003`; Story 5.2 does not repair numeric overflow, which is why AC10 uses it. Plain text (`online`) fails `json.Valid`. An empty payload fails `json.Valid` and on the server with `22P02`; a `nil` payload fails with `23502`. [Source: docs/sprint-change-proposals/2026-09-17-write-pipeline-stall.md#2-evidence--what-postgresql-actually-rejects]

### Log Contract

| Entry | Level | Fields | `operation` |
|-------|-------|--------|-------------|
| `write_rejected` | ERROR | `topic`, `payload_size` (bytes), `duration_us` (`0` for a local rejection), `reason` (`invalid_json` / `sqlstate`), `sqlstate` (five-character code, `reason=sqlstate` only), `error`. **Never the payload body** | `insert` — it reports a failed attempt, like `write_failure` |
| `write_skipped` | DEBUG | `topic`, `reason` (`empty_payload`) | none — it reports a state |
| `write_failure` | ERROR | unchanged | `insert`. Now means "this write will be retried" and only that |
| `health_check` | INFO | existing fields + `rejected_last_interval` (messages discarded by `write_rejected` since the previous entry) | none |

All entries come from the `database` component logger, which already carries `component`, `host` and `database`; do not repeat them. Values go in fields, never interpolated into `msg`. The payload body is excluded because it can be large (about 283 KB for `bridge/definitions`); `topic` and `payload_size` identify the message, and the DEBUG `message_received` entry already carries the body when needed. `write_rejected` is ERROR, not WARN: a discarded message is lost data. [Source: docs/architecture/logging-standards.md; docs/architecture/error-handling-strategy.md#3-runtime-errors---data-integrity-log-and-skip]

### SM Clarifications

Where the ACs leave a detail open, these answers apply. Each gives its source or its reasoning.

- **C1 — `duration_us` on a local rejection is `0`.** AC6 lists the field without a value; `logging-standards.md` (Write rejection row) and the §3 example both give `0`. No round-trip was timed. [Source: docs/architecture/logging-standards.md#domain-fields]
- **C2 — A local rejection leaves `connected` unchanged**, but counts in `RejectedCount()`. `IsConnected()` reports "the outcome of the most recent database interaction" (`client.go:119-121`), and a local rejection is not one. `rejected_last_interval` counts "messages discarded by `write_rejected`", which includes both reasons. [Source: internal/database/client.go; docs/architecture/logging-standards.md]
- **C3 — An empty-payload skip changes no counter and no state:** not `rejectedCount` (AC4), not `writeCount`/`lastWriteAt` (nothing was written — the same reasoning as AC7), not `connected` (no interaction). Consequence, intended: a skipped message does not appear in `processed_last_interval`.
- **C4 — Check order: truncation first (unchanged), then skip, then `json.Valid`, then INSERT.** The skip → repair → validate → INSERT order is fixed by §3's table; keeping truncation first means every entry reports the truncated `topic`, as `write_failure` does today.
- **C5 — `nil` is treated as empty.** `len(nil) == 0`. Class `23` stays in the permanent set anyway: it is part of FR11 and guards the server side. [Source: docs/prd.md FR11]
- **C6 — Error wrapping.** The server-side return wraps both `ErrRejected` and the `*pgconn.PgError` (two `%w`), so callers match the sentinel and tests can still reach the code. The `error` log field on a server rejection is the raw driver error, as in the architecture example; on a local rejection it is the `"message rejected by database: invalid JSON"` error.
- **C7 — `isPermanent` must not index a short code.** The architecture sample's `pgErr.Code[:2]` panics if `Code` has fewer than two bytes. PostgreSQL always sends five characters, but a synthetic `&pgconn.PgError{}` in a test does not. Use `len(pgErr.Code) >= 2` before slicing, or `strings.HasPrefix` per class.
- **C8 — AC11 is mostly already done in `docs/architecture/`.** The PO applied the proposal's §7 on 2026-09-17, ahead of implementation. What remains is reconciliation (Task 8), not authoring.
- **C9 — "The README's data-loss section".** The README has no section with that name. The only statement about message loss is the Features bullet at `README.md:27-28` ("so no message is lost during an outage"); that bullet is the target. The new integration test file also has to appear in the two README lists that enumerate the integration test files.
