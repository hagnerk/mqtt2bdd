# Story 2.4: Implement Graceful Shutdown Handler

## Status

Ready for Review

## Story

**As a** system operator,
**I want** the application to flush all buffered messages before shutdown,
**so that** no data is lost when the container is stopped.

## Acceptance Criteria

> ACs 1–12 are copied verbatim from Epic 2 in `docs/prd.md`. ACs 13–15 fold in QA findings that prior gates explicitly deferred to this story (see Dev Notes → Carry-Forward Findings).

1. `main.go` registers signal handler for SIGTERM and SIGINT using `signal.Notify()`
2. On receiving shutdown signal, log INFO: "Shutdown signal received, flushing buffered messages..."
3. Close MQTT client connection to stop receiving new messages
4. Close message channel to signal database writer goroutine to finish processing
5. Database writer goroutine processes all remaining messages in channel before exiting
6. Wait for database writer goroutine to complete using `sync.WaitGroup` or channel completion signal
7. Log INFO with count of messages flushed: "Flushed <n> buffered messages"
8. Close database connection pool after all messages written
9. Log INFO: "Shutdown complete" and exit with code 0
10. Manual test: Publish messages, send SIGTERM (`docker stop <container>`), verify all buffered messages written before container exits
11. Maximum shutdown time: 30 seconds (configurable via Docker stop timeout)
12. All code passes `go fmt`, `go vet`, and `staticcheck`
13. **(FIND-001)** The startup `defer mqttClient.Disconnect()` and `defer dbClient.Close()` are removed; teardown is performed explicitly in the shutdown sequence (the `defer`s were unreachable because `select {}` blocked forever — see Dev Notes)
14. **(FIND-002 / FIND-004)** Startup `Connect` calls for both MQTT and PostgreSQL use a bounded `context.WithTimeout` instead of `context.Background()`, so a hung broker/DB at startup cannot block indefinitely
15. **(FIND-011)** The MQTT `reconnectLoop` goroutine is cancellable: `Disconnect()` signals it to stop so it does not keep retrying during/after shutdown

### Shutdown Ordering (CRITICAL — do not reorder)

The order below is required for correctness, not stylistic preference:

1. **Disconnect MQTT first.** The Paho message callback (`mqttMessageHandler`) performs a **blocking send** on `msgChan` (main.go:68-73). If `msgChan` were closed while a callback is mid-send, Go panics with "send on closed channel." `Disconnect()` uses a 250 ms quiesce (internal/mqtt/client.go:85-88) which lets in-flight callbacks finish and stops new deliveries. After `Disconnect()` returns, no further callbacks fire, so closing the channel is safe.
2. **Snapshot `len(msgChan)`** — with no producers left, this is exactly the number of buffered messages awaiting flush (used for AC7's count).
3. **Close `msgChan`** — terminates the `for msg := range msgChan` loop in `dbWriterLoop` *after* it drains all remaining buffered messages.
4. **Wait (bounded)** for the writer goroutine to finish via the WaitGroup, racing a `defaultShutdownTimeout` timer.
5. **Close the DB pool** only after the drain completes (or times out).

[Source: docs/architecture/error-handling-strategy.md#5-shutdown-errors-best-effort]

Note on a clean MQTT `Disconnect()` and `reconnectLoop`: with `SetAutoReconnect(false)` (internal/mqtt/client.go:52), a client-initiated `Disconnect()` does not invoke the `ConnectionLostHandler`, so it will not spawn a *new* `reconnectLoop`. AC15's cancellation matters only for the case where a `reconnectLoop` was *already running* (broker was down when the signal arrived) — without cancellation it would keep retrying for up to 10s and ignore shutdown intent. [Source: internal/mqtt/client.go:52-57, 122-142]

### Target Shape of `main()` (illustrative, not prescriptive line-for-line)

```go
func main() {
    cfg, err := config.LoadConfig()
    if err != nil {
        log.Fatalf("configuration error: %v", err)
    }

    l := logger.InitLogger(cfg.LogLevel)
    l.Info("MQTT2BDD starting", "version", Version)

    mqttClient := mqtt.NewClient(cfg, l)
    mqttCtx, mqttCancel := context.WithTimeout(context.Background(), defaultConnectTimeout)
    err = mqttClient.Connect(mqttCtx)
    mqttCancel()
    if err != nil {
        os.Exit(1)
    }

    dbClient := database.NewClient(cfg, l)
    dbCtx, dbCancel := context.WithTimeout(context.Background(), defaultConnectTimeout)
    err = dbClient.Connect(dbCtx)
    dbCancel()
    if err != nil {
        os.Exit(1)
    }

    msgChan := make(chan mqtt.Message, cfg.BufferSize)

    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        dbWriterLoop(msgChan, dbClient)
    }()

    mqttMessageHandler := func(topic string, payload []byte) {
        msg := mqtt.Message{Topic: topic, Timestamp: time.Now(), Payload: payload}
        select {
        case msgChan <- msg:
        default:
            l.Warn("message buffer full, blocking until space available", "buffer_size", cfg.BufferSize)
            msgChan <- msg
        }
    }
    if err := mqttClient.Subscribe("#", mqttMessageHandler); err != nil {
        l.Error("MQTT subscribe failed", "error", err)
        os.Exit(1)
    }

    sigChan := make(chan os.Signal, 1)
    signal.Notify(sigChan, os.Interrupt, syscall.SIGTERM)
    sig := <-sigChan
    l.Info("Shutdown signal received, flushing buffered messages", "signal", sig.String())

    mqttClient.Disconnect()      // Step 1 — stop new messages (AC3)
    buffered := len(msgChan)     // Step 2 — count awaiting flush (AC7)
    close(msgChan)               // Step 3 — signal writer to drain (AC4)

    drained := make(chan struct{})
    go func() { wg.Wait(); close(drained) }()
    select {
    case <-drained: // Step 4 — writer finished (AC5, AC6)
        l.Info("Flushed buffered messages", "count", buffered) // AC7
    case <-time.After(defaultShutdownTimeout): // AC11
        l.Warn("Shutdown timeout exceeded; some buffered messages may not have been flushed", "buffered", buffered)
    }

    dbClient.Close()             // Step 5 (AC8)
    l.Info("Shutdown complete")  // AC9 — natural return ⇒ exit 0
}
```

### Reliability Note (FIND-014 detail)

The ordered teardown and the WaitGroup-vs-timeout race are correct, and the timeout prevents an indefinite hang. The gap is the compound degraded state — **DB down (writer stuck in its 10s retry) + buffer full + shutdown**. In that case a producer goroutine is blocked on the handler's fallback send when `close(msgChan)` runs, panicking the process rather than exiting via the AC11 WARN path. The conditions are narrow, but this story is where `close(msgChan)` makes the pre-existing blocking-send design reachable, and it is precisely the scenario the bounded timeout was meant to handle gracefully. Marked medium severity → reliability CONCERNS.
