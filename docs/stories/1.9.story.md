# Story 1.9: Integrate MQTT Reception with PostgreSQL Persistence

## Status

Done

## Story

**As a** home automation user,
**I want** every MQTT message automatically persisted to PostgreSQL,
**so that** I can analyze historical device data.

## Acceptance Criteria

1. `main.go` implements a message handler that calls `database.InsertMessage()` for each received MQTT message
2. Message handler extracts: MQTT topic as sensor identifier, current timestamp (`time.Now()`), and raw JSON payload
3. Message handler invokes `InsertMessage` in a goroutine to avoid blocking Paho's callback goroutine
4. Successful persistence logged at DEBUG level with sensor name, timestamp, and payload size — satisfied by `InsertMessage`'s existing internal logging in `queries.go` (no duplicate log in the handler)
5. Failed persistence logged at ERROR level with full context but does not crash the application — satisfied by `InsertMessage`'s existing ERROR log; the spawned goroutine checks the returned error and returns silently (InsertMessage has already logged it)
6. Startup sequence reordered so Subscribe happens **after** both MQTT and PostgreSQL are connected: MQTT Connect → DB Connect → Subscribe
7. Manual end-to-end test: Publish MQTT message from `mqtt2bdd-dev-mosquitto` container: `docker exec mqtt2bdd-dev-mosquitto mosquitto_pub -t 'zigbee2mqtt/living_room/thermostat' -m '{"temperature": 21.3, "humidity": 45}'`
8. Verify message appears in `sensor_metrics` table: `docker exec -it mqtt2bdd-dev-postgres psql -U mqtt2bdd -d mqtt2bdd -c "SELECT * FROM sensor_metrics;"`
9. Manual load test: Publish 100 messages rapidly, verify all 100 rows appear in `sensor_metrics`
10. Application startup logs show clear sequence in order: MQTT2BDD starting → MQTT connected → PostgreSQL connected → Subscribed to all topics
11. All code passes `go fmt`, `go vet`, and `staticcheck`

### `main.go` — Target Structure After Story 1.9

The only file modified in this story is `cmd/mqtt2bdd/main.go`. The final structure must be:

```
1. config.LoadConfig()         → fatal if error
2. logger.InitLogger()         → l := ...
3. l.Info("MQTT2BDD starting") → version logged
4. mqtt.NewClient + Connect    → fatal (os.Exit(1)) if error; defer Disconnect
5. database.NewClient + Connect→ fatal (os.Exit(1)) if error; defer Close
6. mqttClient.Subscribe("#", realHandler) → fatal if error
7. select {}                   → block until killed (signal handling in 2.x)
```

The `realHandler` goroutine:

```go
mqttMessageHandler := func(topic string, payload []byte) {
    go func() {
        if err := dbClient.InsertMessage(context.Background(), topic, time.Now(), json.RawMessage(payload)); err != nil {
            // error already logged by InsertMessage
        }
    }()
}
```

**Why goroutine-per-message here:** Paho invokes the message handler in its own goroutine. Calling `InsertMessage` synchronously inside Paho's goroutine would block message reception during DB latency. Spawning a goroutine-per-message decouples reception from persistence for story 1.9. This approach is intentionally simple — story 2.1 will replace it with a buffered channel + single DB writer goroutine to provide backpressure, deduplication, and outage buffering.

**No `Message` struct needed yet:** The `Message` struct (with `Topic`, `Timestamp`, `Payload` fields) lives in `internal/mqtt/types.go` per the architecture's source tree, but it is introduced in story 2.1 when the channel-based approach is wired. Story 1.9 passes arguments to `InsertMessage` directly — no intermediate struct.

**`json.RawMessage(payload)` conversion:** `json.RawMessage` is a `type RawMessage []byte`. The conversion `json.RawMessage(payload)` is a zero-copy type assertion. Paho does not reuse the payload slice between callbacks, so no defensive copy is needed.
