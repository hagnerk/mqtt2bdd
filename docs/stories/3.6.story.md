#### FIND-019 — `duration_ms` truncation (AC13)

**Re-confirmed live for this draft**: `internal/database/queries.go` lines 39, 58, 66 all read
`"duration_ms", elapsed.Milliseconds()`. `time.Duration.Milliseconds()` truncates toward zero — any
write completing in under 1 ms (plausible against the containerized Postgres this project runs in
`dev/`, and increasingly likely on faster hardware or under low load) reports `duration_ms=0`,
indistinguishable from a genuinely instantaneous write and useless as a performance signal. Gate 3.1
independently observed `duration_ms=26` in its own environment — not yet degenerate there, but the
truncation risk was explicitly called "still latent rather than degenerate in this environment," i.e.
a live risk, not a hypothetical one. [Source: internal/database/queries.go:39,58,66;
docs/qa/gates/3.1-create-production-multi-stage-dockerfile.yml:45]

**FIND-019 Disposition — switch to microseconds (`duration_us`), not float milliseconds.** Gate 2.5's
own note floated two options: (a) `elapsed.Microseconds()` renamed `duration_us`, or (b) keep
milliseconds but as `elapsed.Seconds()*1000` (a `float64`). This story picks **(a)**, for two reasons:

1. **No floating point enters the log schema.** Every other numeric field this codebase logs today —
   `payload_size`, `buffer_used`, `buffer_capacity`, `processed_last_interval`, the four `pool_stats`
   counters, `attempt`, `count` — is an integer. `buffer_utilization_percent` is the one deliberate
   exception, and it is deliberately rounded to one decimal specifically so it stays "a number a log
   processor can aggregate rather than 33.333333333333336" (the exact reasoning `main.go`'s own comment
   on `bufferUtilizationPercent` gives). A float `duration_ms` would introduce the same class of
   precision noise this codebase has otherwise consistently avoided, purely to keep a field name
   unchanged.
2. **`time.Duration.Microseconds()` already exists and returns `int64`**, exactly parallel to
   `.Milliseconds()` — the code change is a mechanical one-line swap at each of the three call sites,
   not a new computation, and three orders of magnitude of resolution gain (microseconds vs.
   milliseconds) comfortably covers any write this project's own scale (a single writer goroutine,
   ~1 million messages/day per the schema's own `BIGINT` sizing rationale in
   `docs/architecture/database-schema.md`) will ever produce.

The field is **renamed**, not kept as `duration_ms` with different units — a silent unit change behind
the same field name is exactly the kind of trap a log-field contract document (`logging-standards.md`)
exists to prevent; a consumer (dashboard, alert, or a future story's own code) filtering or graphing
`duration_ms` must not silently start receiving values 1000× larger than before.
