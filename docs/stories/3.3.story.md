12. **(PO-mandated, carried from gate 2.2, re-homed here by gate 3.2 / FIND-010)** After the MQTT client
    reconnects following a broker outage, if re-subscription fails, `internal/mqtt/client.go`'s
    `reconnectLoop` must retry the re-subscription — not log once and give up — until it succeeds or
    shutdown is signalled. The integration suite must reproduce a real broker restart (`docker compose stop
    test-mosquitto` / `start test-mosquitto`, which forgets every subscription server-side) and assert on
    the **observable outcome**: a message published after the broker comes back is received and persisted,
    not merely that `IsConnected()` is true. Because a real broker cannot be made to reject a specific
    `Subscribe` call on demand without ACL machinery this project does not have, the retry-until-success
    *mechanism* itself is additionally proven by a fast, deterministic unit test against a fake broker
    client that scripts a `Subscribe` failure before succeeding — see Dev Notes → AC12.
13. **(PO-mandated, carried from gate 2.4 / FIND-016)** `cmd/mqtt2bdd/main.go`'s shutdown drain path
    (`insertWithRetry`, `dbWriterLoop`'s drain branch) uses `context.Background()` and a bare `time.Sleep`,
    so a database outage during shutdown can run the drain past `defaultShutdownTimeout` while
    `dbClient.Close()` tears down the pool underneath it. Bind the drain path to a context that shares
    the same 30 s budget as `main`'s own shutdown timeout, and make the inter-retry wait interruptible, so
    the two converge instead of racing. Prove it with an integration test that exercises real I/O (a real,
    briefly-unavailable test-postgres) — see Dev Notes → AC13.
14. **(PO-mandated, carried verbatim from gate 2.5, restated in every gate since)** A `TestGracefulShutdown`
    integration test must assert the `message_dropped` WARN (`main.go:242`) fires under a genuine
    full-buffer-at-shutdown race, and must assert that `healthWG.Wait()`'s placement — after the drain
    select, before `dbClient.Close()` — actually holds under real timing, not by inspection. See Dev Notes
    → AC14.

## Dev Notes

### Previous Story Insights (Stories 3.1, 3.2)

- **The artefacts this story reuses.** `Dockerfile` (root, Story 3.1) is a two-stage build producing a
  ~18.5 MB static binary; the test stack's `mqtt2bdd` service builds from it unmodified. `docker-compose.prod.yml`
  (Story 3.2) established the pattern this story mirrors: short service names (`postgres`, `mosquitto`,
  `mqtt2bdd`) with an explicit `container_name:` carrying the environment prefix, explicit `name:` keys on
  the network to dodge the Compose project-prefix trap, parameterised host ports so stacks can coexist,
  and the three health-check probes (`pg_isready`, `mosquitto_sub` against `$SYS/broker/uptime`, `netstat`
  against the broker's `ESTABLISHED` socket). [Source: docs/stories/3.1.story.md, docs/stories/3.2.story.md]
- **The Compose project-name prefix trap.** A bare `name: mqtt2bdd-test` plus explicit `name:` on the
  network and no top-level `version:` key avoids Compose silently creating
  `mqtt2bdd-test_mqtt2bdd-test-network`. [Source: docs/stories/3.2.story.md#network-volumes-and-the-compose-name-prefix]
- **Commands run inside Docker, never on the host — with one sanctioned exception.** `docker compose exec
  go-dev <cmd>` from `dev/` for all Go tooling. `docker build`, `docker run` and `docker compose -f
  <other-file>` are daemon operations and are the established exception (Story 3.1/3.2 precedent) — this
  story's entire subject, `test/docker-compose.yml` and `test/run-integration-tests.sh`, is itself that
  same class of exception for the commands that operate the test stack.
- **`docker compose` (space), never `docker-compose` (hyphen).** Corrected by the PO at Story 3.2
  validation: the hyphenated form happens to work on this host too, but it is a legacy alias whose
  presence varies by installer. Every command in this story's script and Dev Notes uses the space form.
  [Source: docs/stories/3.2.story.md#deviation-ac11]
- **Nothing is currently running that this story would collide with.** Verified live while drafting:
  `docker ps` shows only `mqtt2bdd-dev-postgres` (5432), `mqtt2bdd-dev-mosquitto` (1883) and
  `mqtt2bdd-dev-go-dev` (2345) among this project's containers; no `mqtt2bdd-prod-*` or `mqtt2bdd-test-*`
  container, network or volume exists. Story 3.2's cleanup (`down -v`, image removal) is confirmed
  complete — nothing was left running from that story.

tests with no relation to shutdown. So this is new test authorship, not "fix an existing test."

The reason it is 3.3's and not 3.4's: `message_dropped` only fires when a producer is mid-send against a
**full buffer** at the **exact moment** `done` closes — a race between a real goroutine and a real signal.
`healthWG` ordering is a claim about **goroutine teardown sequencing under real timing**, not about a pure
function's return value. Neither is reachable with `t.Setenv` and an in-memory fake the way `config_test.go`
or a table-driven `internal/mqtt` test is. Both need a real running process, a real signal, and real
timing — which is exactly `test-strategy-and-standards.md`'s own definition of an integration test
(`//go:build integration`, real external services), not a unit test. Story 3.4's own AC1–AC4 describe
`config_test.go`, `logger`, `internal/mqtt/client_test.go` and `internal/database/client_test.go` — package
-level unit-test coverage. `cmd/mqtt2bdd`'s shutdown orchestration is not in that list, and gate 2.4 said so
directly: *"Graceful shutdown still has zero automated coverage by design (orchestration lives in `main()`);
this critical data-safety path relies on manual E2E until `TestGracefulShutdown` lands in Story 3.3."*
Ruling: **AC14 stays in 3.3.**

### Current Behaviour: FIND-010 (`internal/mqtt/client.go:145-173`)

```go
func (c *Client) reconnectLoop() {
	for attempt := 1; ; attempt++ {
		select {
		case <-time.After(defaultMQTTReconnectInterval):
		case <-c.shutdown:
			c.logger.Info("MQTT reconnect cancelled, shutting down", "event", "reconnect_cancelled")
			return
		}
		token := c.pahoClient.Connect()
		<-token.Done()
		if err := token.Error(); err != nil {
			c.logger.Error("MQTT reconnection failed", "event", "reconnect_failed", "operation", "reconnect", "attempt", attempt, "error", err)
			continue
		}
		c.logger.Info("MQTT reconnected successfully", "event", "reconnected")
		if c.subscribedHandler != nil {
			if err := c.Subscribe(c.subscribedTopic, c.subscribedHandler); err != nil {
				c.logger.Error("MQTT re-subscription failed after reconnect", "event", "resubscribe_failed", "operation", "subscribe", "error", err)
			}
		}
		return   // <-- returns whether Subscribe succeeded or not
	}
}
```

The **CONNECT** retry (the outer `for` loop) is already correct — it keeps retrying every
`defaultMQTTReconnectInterval` (10 s) until the TCP/MQTT connect succeeds. The bug is narrower and one level
down: once *connect* succeeds, `Subscribe` is attempted exactly **once**. If it fails, the function
`return`s unconditionally. `c.pahoClient.IsConnected()` is now `true` (the broker link is up), but no
subscription exists, so no message ever reaches `handler` again. `healthCheckLoop` (`main.go:104-157`) calls
exactly `mqttClient.IsConnected()` for its `mqtt_status` field — it has no way to see that the subscription
is gone, so it reports `mqtt_status=connected` forever while the pipeline is silently dead.

### AC12 — The Fix

Replace the single `if`/`return` with a retry loop, reusing the same cadence already used for the connect
retry:

```go
c.logger.Info("MQTT reconnected successfully", "event", "reconnected")
if c.subscribedHandler != nil {
	for {
		err := c.Subscribe(c.subscribedTopic, c.subscribedHandler)
		if err == nil {
			break
		}
		// Subscribe() itself already logged the generic subscribe_failed (client.go:138).
		// This entry is the distinct, documented resubscribe_failed event — the one
		// operators filter on to see specifically "a reconnect's subscribe attempt
		// failed" — moved here from the old single-shot version so it now fires on
		// EVERY failed attempt, not just the first.
		c.logger.Error("MQTT re-subscription failed after reconnect", "event", "resubscribe_failed", "operation", "subscribe", "error", err)
		select {
		case <-time.After(defaultMQTTReconnectInterval):
		case <-c.shutdown:
			c.logger.Info("MQTT reconnect cancelled, shutting down", "event", "reconnect_cancelled")
			return
		}
	}
}
return
```

No new `event` value is introduced — `resubscribe_failed` (already in `logging-standards.md`'s `mqtt`
vocabulary) now appears once per failed attempt instead of once total, and `Subscribe()`'s own
`subscribe_failed` still fires underneath it on every call as it always has, unchanged.

### AC12 — Unit Test (`internal/mqtt/client_test.go`, new, no build tag)

`mqtt.Client` (the Paho type `Client` embeds as `pahoClient`) is an **interface**
(`github.com/eclipse/paho.mqtt.golang@v1.5.0/client.go:64`), with `Connect() Token`, `Subscribe(topic
string, qos byte, callback MessageHandler) Token`, `Disconnect(quiesce uint)`, `IsConnected() bool` among
its methods. `mqtt.Token` is also an interface (`Wait() bool`, `Done() <-chan struct{}`, `Error() error`).
Both are narrow enough to fake by hand — no third-party mock library needed, matching
`test-strategy-and-standards.md`'s "avoid over-mocking... mock at system boundaries" principle: the Paho
client is exactly such a boundary.

Because `NewClient` does not expose a way to inject a fake `pahoClient`, this is a **white-box test**
(`package mqtt`, same package as `client.go`) that constructs `&Client{pahoClient: fake, subscribedTopic:
"#", subscribedHandler: someHandler, shutdown: make(chan struct{}), logger: ...}` directly, bypassing
`NewClient` — exactly the pattern the "Package convention" guidance under
`test-strategy-and-standards.md#test-organization` prescribes for unexported behaviour.

Design:
- A `fakeToken` whose `Done()` returns an already-closed channel and `Error()` returns a scripted error (or
  `nil`).
- A `fakePahoClient` with a `subscribeCalls int` counter and a `subscribeFailures int` field: its
  `Subscribe` method returns an error token for as long as `subscribeCalls <= subscribeFailures`, then a
  success token.
- Call `reconnectLoop()` directly (unexported, same package) after simulating a connection loss (or, more
  simply, test the resubscribe segment in isolation if refactoring it into a small helper is cleaner — the
  Dev agent's call, as long as the retry-until-success behaviour is what's actually exercised).
- To keep the test fast, do not wait out the real `defaultMQTTReconnectInterval` (10 s): either factor the
  interval into a `var` the test can shrink for its own run (acceptable, narrowly scoped), or drive the
  fake's `Subscribe` to fail zero or one time so at most one 10 s wait is incurred — document whichever
  choice is made and why in the Dev Agent Record.
- Assert: `fakePahoClient.subscribeCalls > 1` (proves a retry happened, not just one attempt), and the loop
  eventually returns having subscribed successfully.

### AC12 — Integration Test (`cmd/mqtt2bdd/mqtt_reconnect_integration_test.go`, new, `//go:build integration`)

`TestMQTTReconnect` — reproduces the **observable**, user-visible half of FIND-010 against the real test
stack (this is the "at minimum prove reconnect+resubscribe succeeds" floor the orchestrating brief set,
since forcing a real broker to reject one specific `Subscribe` call on demand needs ACL machinery this
project does not have and would be too brittle to script reliably):

1. Build and start the `mqtt2bdd` binary as a subprocess (see How Integration Tests Reach the Test Stack,
   below), pointed at `mqtt2bdd-test-postgres`/`mqtt2bdd-test-mosquitto` by container DNS.
2. Wait for `event=startup_complete` on its stdout.
3. Publish one message via the test broker; poll `sensor_metrics` until it appears.
4. `docker stop mqtt2bdd-test-mosquitto` then `docker start mqtt2bdd-test-mosquitto` (via `os/exec`,
   invoking the host's `docker` CLI — see justification below). A **restarted** container, not a network
   partition: Mosquitto's default config keeps no subscription state across a process restart, so the
   client's re-`Subscribe` call is genuinely load-bearing here, not a formality — this is the most faithful
   reproduction of FIND-010's actual failure condition available without ACL tooling.
5. Wait for `event=reconnected` then `event=subscribed` on the subprocess's stdout (bounded wait, e.g. 30 s
   — well past `defaultMQTTReconnectInterval`).
6. Publish a **second**, distinctly-tagged message. Poll `sensor_metrics` for it. **Before the fix, this
   message is silently lost forever** — this is the exact regression AC12 exists to prevent.
7. Send `SIGTERM` to the subprocess, wait for exit 0, and confirm the second message really is present in
   `sensor_metrics`. Fail the test otherwise.

### Current Behaviour: FIND-016 (`cmd/mqtt2bdd/main.go:44-78, 253-284`)

```go
func insertWithRetry(dbClient *database.Client, msg mqtt.Message) {
	for {
		err := dbClient.InsertMessage(context.Background(), msg.Topic, msg.Timestamp, json.RawMessage(msg.Payload))
		if err == nil {
			return
		}
		time.Sleep(defaultRetryIntervalOnDatabaseFailure) // bare Sleep — not interruptible
	}
}
```

`dbWriterLoop`'s drain branch (entered once `done` is closed) calls this same function for every buffered
message, in sequence. `main()`'s shutdown sequence races `wg.Wait()` (which only returns once `dbWriterLoop`
has drained everything) against its own separate `time.After(defaultShutdownTimeout)` (30 s). If the drain
is still stuck — e.g. the database is down and `insertWithRetry` is mid-`Sleep` — `main()`'s `select` times
out, logs `flush_timeout`, and proceeds to `healthWG.Wait()` then `dbClient.Close()` **regardless of whether
the drain goroutine is still running**. `dbClient.Close()` tears down the pgx pool while `insertWithRetry`
may still be calling `InsertMessage` against it — the writer's next `Exec` then fails, which is at least
not a panic, but the two clocks (`main`'s 30 s timeout and the drain's unbounded retry) are racing rather
than converging, and the drain can in principle run indefinitely past the 30 s the operator was promised.

### AC13 — The Fix

A single shared 30 s budget, armed at the moment shutdown begins, threaded into the drain path only —
steady-state (non-drain) retries stay unbounded, preserving the "no message lost during a database outage"
invariant from Stories 1.8/2.3.

```go
// New constant alongside the existing ones (main.go:20-34):
const defaultInsertAttemptTimeout = 5 * time.Second // bounds ONE insert attempt so a hung
                                                     // (not refused) database cannot block a
                                                     // retry loop forever, in either state.

// insertWithRetry now takes a ctx. Steady state passes context.Background() (unbounded
// retries, unchanged). The drain path passes shutdownCtx (below).
func insertWithRetry(ctx context.Context, dbClient *database.Client, msg mqtt.Message) {
	for {
		attemptCtx, cancel := context.WithTimeout(ctx, defaultInsertAttemptTimeout)
		err := dbClient.InsertMessage(attemptCtx, msg.Topic, msg.Timestamp, json.RawMessage(msg.Payload))
		cancel()
		if err == nil {
			return
		}
		select {
		case <-time.After(defaultRetryIntervalOnDatabaseFailure):
		case <-ctx.Done():
			return // shutdown budget exhausted — abandon this message, drain moves on
		}
	}
}

func dbWriterLoop(msgChan <-chan mqtt.Message, dbClient *database.Client, done <-chan struct{}, shutdownCtx context.Context) {
	for {
		select {
		case msg := <-msgChan:
			insertWithRetry(context.Background(), dbClient, msg) // steady state: unbounded, unchanged
		case <-done:
			for {
				select {
				case msg := <-msgChan:
					insertWithRetry(shutdownCtx, dbClient, msg) // drain: bounded
				default:
					return
				}
			}
		}
	}
}
```

In `main()`, create `shutdownCtx` cheaply at startup (no timer runs until armed) and arm it exactly when
shutdown begins:

```go
// Alongside `done := make(chan struct{})`, near main.go:207:
shutdownCtx, shutdownCancel := context.WithCancel(context.Background())
defer shutdownCancel()

// ... unchanged until the signal handler, main.go:261-263:
mqttClient.Disconnect()
buffered := len(msgChan)
close(done)
time.AfterFunc(defaultShutdownTimeout, shutdownCancel) // arms the SAME 30s budget main's own
                                                        // select below already races, from the
                                                        // same starting instant — the two
                                                        // converge instead of racing.
```

Why this design and not a channel-of-context or restructuring `dbWriterLoop`'s launch order:
`context.WithCancel` costs nothing until cancelled, so creating it at startup (long before any shutdown
signal) is free — unlike `context.WithTimeout`, whose clock would start immediately and expire long before
a real SIGTERM arrives if created at startup. `time.AfterFunc` at the exact moment of `close(done)` gives
the drain path a timeout that starts counting from the same instant as `main`'s own `time.After` a few
lines below — both bounded by `defaultShutdownTimeout`, both starting together, so they finish together
instead of one leaking past the other.

### AC13 — Integration Test

Folded into `cmd/mqtt2bdd/shutdown_integration_test.go` (same file as AC14, Task 6) as a second test
function, e.g. `TestShutdownDrainBounded`:

1. Start the subprocess against the real test stack, `BUFFER_SIZE` large enough to hold several messages.
2. Publish a handful of messages, wait for them to persist (proves the pipeline works normally).
3. Publish one more message, then **immediately** `docker stop mqtt2bdd-test-postgres` before it can be

4. Send `SIGTERM` to the subprocess. Assert the process exits **within `defaultShutdownTimeout` plus a
   small margin** (e.g. 35 s, not indefinitely) — this is the load-bearing assertion: before the fix, a

5. Restart `mqtt2bdd-test-postgres` (cleanup for the next test) and assert the stdout shows either

   hanging past the bound or exiting non-zero.

### AC14 — Test Design (`TestGracefulShutdown`, same file, Task 6)

```
1. Build the mqtt2bdd binary once for the package (TestMain or a sync.Once helper).
2. Start it as an os/exec.Cmd subprocess with BUFFER_SIZE=2 (small enough to fill fast) against
   the real test-postgres/test-mosquitto, LOG_LEVEL=DEBUG, stdout piped and scanned line-by-line
   into a slice as it arrives (a goroutine draining cmd.Stdout so the pipe never blocks the child).
3. Wait for a line containing `event=startup_complete`.
4. Publish 3 messages back-to-back via the test broker (BUFFER_SIZE=2 means the 3rd send blocks
   the producer, taking the buffer-full branch at main.go:234-236).
5. While the producer is blocked (a short, deliberate sleep after publishing to let the app reach
   the `event=buffer_full` WARN — assert that line appears, confirming timing), send SIGTERM to the
   subprocess.
6. The blocked producer's select (main.go:239-244) now races msgChan<-msg against <-done; done
   wins because msgChan has no drained slot yet — assert a line containing `event=message_dropped`
   appears with a `topic=` field matching what was published.
7. Wait for process exit. Assert exit code 0.
8. Assert log ordering: no line containing `event=health_check` has a `time=` value later than the
   `event=shutdown_complete` line's. This is the healthWG-ordering assertion: it holds because
   healthWG.Wait() (main.go:281) sits after the drain select and before dbClient.Close() (main.go:283).
   Given the 60 s health-check interval far exceeds this short test's runtime, zero `health_check`
   lines is the expected, and acceptable, case — the assertion is "none after shutdown_complete", not
   "at least one before it".
```

**Log format note:** `internal/logger/logger.go` uses `slog.NewTextHandler` (confirmed by reading the
source), **not** JSON — entries are space-separated `key=value` pairs, e.g. `time=2026-07-25T12:00:00.000Z
level=INFO msg="MQTT2BDD starting" component=main event=starting version=dev`. A simple per-line regexp
(`event=(\S+)`, `time=(\S+)`) is sufficient to extract what these assertions need; do not reach for a JSON
parser, and do not assume `logger.InitLogger` ever switches handlers based on environment.

Timing note: forcing the exact producer-blocked-then-SIGTERM race deterministically needs the test to
publish fast enough that the buffer fills before the harness proceeds. Use `BUFFER_SIZE=2` and publish 3+
messages in a tight loop with no delay; if flakiness appears during implementation, increase the message
count rather than adding a fixed sleep before SIGTERM (a longer buffer-full window is more robust than a
timing guess).

### How Integration Tests Reach the Test Stack

The Go integration test binary itself runs inside a **throwaway `golang:1.23-alpine` container attached to
`mqtt2bdd-test-network`** (started by `test/run-integration-tests.sh`, not by `docker compose`), so it
resolves `mqtt2bdd-test-postgres` / `mqtt2bdd-test-mosquitto` by container DNS directly — no
`host.docker.internal`, no dependency on the exposed host ports, and no dependency on `go-dev` joining a
network it has no other reason to be on. The exposed host ports (AC4, 5433/1884) exist for a different,
equally real purpose: a human operator running `psql`/`mosquitto_pub` against the test stack directly from
the host, or from `go-dev` via `host.docker.internal` (verified working under this project's OrbStack
environment; a bare-Linux CI runner would need `--add-host=host.docker.internal:host-gateway`, out of scope
here since it would mean editing `dev/docker-compose.yml`, which this story does not touch).

The `mqtt2bdd` service **cannot** run the Go test suite internally — it is built from the production
`Dockerfile`'s `runtime` stage (`alpine:3.23` plus the compiled binary and CA certificates only, no Go
toolchain, established as fact when Story 3.1/3.2 closed FIND-024). This is also true of the architecture
document's own reference script (`docker-compose exec -T mqtt2bdd-test-app go test ...`), which would fail
identically against the shipped image — a stale detail this story does not need to reconcile explicitly
(AC15's two edits are the only reconciliation this story makes), but the Dev agent should not copy that
line from the architecture doc verbatim.

### The MQTT ClientID Constraint

`internal/mqtt/client.go:50` hardcodes `opts.SetClientID("mqtt2bdd")`. Two live instances of the binary
connecting to the same broker with the same client ID cause Mosquitto to disconnect whichever connected
first (standard MQTT client-ID-uniqueness behaviour) — a real constraint found while drafting this story,
not a hypothetical. Consequence: the compose-managed `mqtt2bdd` service (used only for the shell script's
basic smoke test) must be stopped (`docker compose stop mqtt2bdd`) before any Go-level integration test
spawns its own subprocess of the same binary, and the `cmd/mqtt2bdd` integration test functions must run
sequentially, not with `t.Parallel()`, since each spawns its own instance of the same hardcoded client ID
against the same broker. This is the one place this story's Dev Notes deliberately override the project's
general "use `t.Parallel()` where appropriate" preference (`docs/prd.md` Story 3.4 AC8) — noted here so
Story 3.4's Dev agent does not "fix" it by parallelising later.

# Integration test runner for mqtt2bdd (AC7). Brings up the isolated test stack, runs a
# basic pub->persist smoke test against the compose-managed app, then runs the full Go
# integration suite (which exercises FIND-010/FIND-016/message_dropped scenarios via its

set -u

cleanup() {
  echo "==> Tearing down test stack"
  $COMPOSE down -v --remove-orphans
}
trap cleanup EXIT INT TERM

echo "==> Building and starting test stack"
if ! $COMPOSE up -d --build; then
  echo "FAIL: test stack did not start"
  exit 1
fi

echo "==> Waiting for all services to report healthy"
deadline=$(( $(date +%s) + 90 ))
while true; do
  unhealthy=$($COMPOSE ps --format '{{.Name}} {{.Health}}' | grep -v ' healthy$' || true)
  if [ -z "$unhealthy" ]; then
    break
  fi
  if [ "$(date +%s)" -ge "$deadline" ]; then
    echo "FAIL: services did not become healthy within 90s:"
    echo "$unhealthy"
    exit 1
  fi
  sleep 2
done
echo "All services healthy."

echo "==> Basic smoke test: publish -> persist -> verify"
if ! $COMPOSE exec -T mosquitto mosquitto_pub -h localhost -t 'integration/smoke' -m '{"value": 42}'; then
  echo "FAIL: mosquitto_pub failed"
  exit 1
fi
sleep 2
rows=$($COMPOSE exec -T postgres psql -U mqtt2bdd -d mqtt2bdd -t -c \
  "SELECT COUNT(*) FROM sensor_metrics WHERE sensor='integration/smoke';" | tr -d '[:space:]')
if [ "$rows" -lt 1 ] 2>/dev/null; then
  echo "FAIL: smoke-test message not found in sensor_metrics (rows=$rows)"
  exit 1
fi
echo "Smoke test passed: message persisted."

echo "==> Stopping compose-managed mqtt2bdd (releases the MQTT client ID for the Go test suite)"
$COMPOSE stop mqtt2bdd

echo "==> Running Go integration test suite"
if ! docker run --rm \
    --network mqtt2bdd-test-network \
    -v "$(pwd):/app" -w /app \
    golang:1.23-alpine \

  exit 1
fi

echo "==> All integration tests passed."

**Decisions made where the story was ambiguous or under-specified (all conservative, all
documented here rather than left silent):**

1. **Docker socket + Docker CLI added to the throwaway `golang:1.23-alpine` test-runner container**
   in `test/run-integration-tests.sh`. The story's reference script and Dev Notes (AC12 → Integration
   Test) explicitly require the Go integration tests themselves to invoke `docker stop`/`docker
   start` against the test containers "via the host's `docker` CLI", but neither the reference
   script nor Dev Notes actually equip that container with the socket or the CLI binary needed to do

   AC12/AC13 test design executable at all; it does not change the stack's shape, ports, naming, or
   any other AC.
2. **`-p 1` added to the `go test -tags=integration` invocation.** `go test ./...` runs different
   packages' test binaries concurrently by default. `internal/database`'s pre-existing (Story 1.8)
   integration suite does ordinary inserts against the same live `test-postgres`/`test-mosquitto`
   that `cmd/mqtt2bdd`'s tests in this story deliberately stop mid-test — without serializing
   package execution, that is a genuine cross-package race, not a hypothetical one. `-p 1` forces
   one package's tests to run at a time.
3. **`-e MQTT_BROKER=... -e POSTGRES_HOST=...` (etc.) added to the same `docker run` invocation.**
   `go test -tags=integration ./...` also builds and runs `internal/database/integration_test.go`
   (pre-existing, Story 1.8), whose `TestMain` calls `config.LoadConfig()` directly against `os.Getenv`
   — independent of `cmd/mqtt2bdd`'s own subprocess env map. Without these flags the whole suite
   failed immediately with "required environment variable MQTT_BROKER is not set." Values match
   `test/docker-compose.yml`'s `mqtt2bdd` service exactly.
4. **`defaultMQTTReconnectInterval` changed from `const` to `var`** in `internal/mqtt/client.go`,
   specifically so `client_test.go` can shrink it for the duration of its own test run (documented
   in the var's own comment) rather than incurring a real 10s wait per retry attempt in a unit test.
   Matches the Dev Notes' own explicitly-sanctioned option ("factor the interval into a `var` the
   test can shrink for its own run — acceptable, narrowly scoped").
5. **`dockerStart` (test helper) waits for the container to report Docker-healthy before returning**,
   not just for the process to start. First full run of `run-integration-tests.sh` failed
   `TestGracefulShutdown` with a spurious "PostgreSQL ping failed: connection refused" because the
   *previous* test's cleanup issued `docker start mqtt2bdd-test-postgres` and returned immediately,
   while Postgres itself was still initialising when the next subprocess's one-shot,
   no-retry `dbClient.Connect()` ran. Fixed by polling `docker inspect --format
   '{{.State.Health.Status}}'` until `healthy` inside `dockerStart` itself, so every call site gets a
   genuinely ready container.
6. **`TestGracefulShutdown` redesigned mid-implementation** (see AC14 above) after a first full run
   showed the original design — a 40-message burst against a *live* database, racing SIGTERM against

   lose. Fixed by stopping `test-postgres` before the burst, which removes the race rather than
   narrowing it, per the explicit guidance to do so.
