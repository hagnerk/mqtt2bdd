### The Prerequisites Contradiction

Worth calling out separately because it is the one place this story must edit existing prose rather
than add to it.

`README.md:153-155` currently says Docker and Docker Compose are "the only hard requirement; the
entire development workflow is containerized, so no host Go installation is needed to run the
application."

**[Corrected at PO validation — the draft misidentified which clause is wrong.]** The draft said the
sentence "is false in its final clause" and that "its last five words overreach". It is not. "No host
Go installation is needed to run the application" stays true for a downloaded binary — more true, in
fact. The clause that stops being true is **"the only hard requirement"**: a user who downloads a
release binary needs neither Docker nor Go, so Docker is not a hard requirement for *running* the
application at all, only for developing on it.

This matters because the two clauses call for different edits. Fixing the tail would leave the actual
contradiction in place.

The fix is small — scope "the only hard requirement" to the development workflow and point at
Installation for the run-it path. It is in scope because AC1 explicitly frames Installation as "the
path for running the application", and shipping a README that contradicts itself two sections apart
would be a defect this story introduced.

### Findings

**DOC-003 — medium: failed downloads do not fail.** Every download command in the section is `curl -LO` without `-f`. On an HTTP error, curl saves the error body under the requested filename and exits 0. Walked exactly as written today, the Latest path went like this:

- `curl -LO …/latest/download/mqtt2bdd_linux_amd64.tar.gz` → exit 0, a 9-byte file containing `Not Found`.
- `curl -LO …/latest/download/checksums.txt` → exit 0, a 9-byte `Not Found`.
- `sha256sum --ignore-missing -c checksums.txt` on macOS → `WARNING: 1 line is improperly formatted`, **exit 0**.
- `tar -xzf mqtt2bdd_linux_amd64.tar.gz` → `Unrecognized archive format`, which reads as a corrupted download.

A verification step that exits 0 on nothing is the failure this section exists to prevent. The range pattern has the same flaw, plus an unguarded empty result. With no `v1.x` release, `TAG` is empty, the URL becomes `releases/download//mqtt2bdd__linux_amd64.tar.gz`, and `Not Found` is again saved silently, exit 0. The latest-path symptom will disappear once `v1.0.0` exists. The flaw will not: a mistyped tag, a rate-limited API call or a future release gap all hit it. Suggested fix: `curl -fLO` everywhere, `[ -n "$TAG" ] || { echo "no matching release" >&2; exit 1; }` in the range pattern, and optionally one sentence saying the latest URLs serve nothing until the first non-pre-release.

**DOC-004 — low: the documented first run is not what an unconfigured user sees.** Extract and run shows a bare `./mqtt2bdd` printing `msg="MQTT2BDD starting" … event=starting`. What the binary still needs then says that, without environment variables, the application "logs `event=starting` and then exits non-zero when it fails to connect". Neither is true without configuration. `main.go` loads the configuration at `:200` and exits at `:203`, **before** the `starting` log at `:210`. Run with an empty environment (`env -i`), the released binary's only output is `level=ERROR msg="configuration error" event=config_load_failed … error="required environment variable MQTT_BROKER is not set"`, then exit 1. The claimed output appears only once the required variables are set; if the broker is then unreachable, it is followed by a connection failure. **Why it passed on 2026-07-31:** the Dev and QA both ran the binary inside `go-dev`, which carries the dev configuration. I made the same mistake in today's Story 4.3 re-review, where it was harmless because that assertion assumes configuration. The error message names the missing variable, so a user is not stuck, only told the wrong thing to expect. Suggested fix: document both outcomes, and verify any documented run with `env -i`.

**DOC-005 — low: the Gatekeeper step fails after the README's own download.** The step `xattr -d com.apple.quarantine ./mqtt2bdd` is presented as required once. After the README's `curl` download, the files carry only `com.apple.provenance` and no quarantine attribute, so the command prints `No such xattr: com.apple.quarantine` and exits 1. With a simulated browser download (quarantine written on the archive), command-line `tar` does propagate the attribute to the binary, and the README command clears it. The step is right for browsers and confusing for curl. For the record: the binary is ad-hoc linker-signed (`codesign`: `Signature=adhoc`), not Developer ID signed, and `spctl --assess --type execute` rejects it, so "unsigned" is accurate in the sense that matters. Suggested fix: scope the step to browser downloads, or write `xattr -d com.apple.quarantine ./mqtt2bdd 2>/dev/null || true`.
