# Story 2.6: Add Application Health Monitoring Logs

## Status

Done

## Story

**As a** system operator,
**I want** periodic health status logs,
**so that** I can verify the application is running correctly.

## Acceptance Criteria

> ACs 1, 3, 5, 6, 8, 9 and 10 are copied verbatim from Epic 2 in `docs/prd.md`. AC2, AC4 and AC7 are reworded to reflect three documented deviations (see Dev Notes → Deviation: AC2/AC7 interpolated message, and Dev Notes → Deviation: AC4 database status). AC11 and AC12 fold in two QA findings that gate 2.5 deferred to a follow-up story (see Dev Notes → Carry-Forward Findings).

1. Implement periodic health check goroutine running every 60 seconds
2. Health check logs at INFO level with structured fields conveying MQTT status, database status and buffer occupancy — `event=health_check`, `mqtt_status=<connected|disconnected>`, `db_status=<connected|disconnected>`, `db_last_write_age_s=<n|-1>`, `buffer_used=<n>`, `buffer_capacity=<n>`, `buffer_utilization_percent=<pct>`, `processed_last_interval=<n>`. This is the complete field set of the entry; AC4, AC5 and AC7 each govern one of the last four (see Dev Notes → Deviation: AC2/AC7 interpolated message)
3. MQTT connection status verified using client `IsConnected()` method
4. Database connection status derived from the outcome of the most recent write, seeded by the startup `Ping` — **no explicit `Ping` in the health check**. The age of the last successful write is reported alongside it as `db_last_write_age_s` (see Dev Notes → Deviation: AC4 database status)
5. Buffer utilization calculated from channel length
6. If buffer utilization >80%, log WARNING: "Message buffer >80% full, possible backpressure"
7. Health check includes message processing rate as a `processed_last_interval` field on the same `health_check` entry: the number of messages written since the previous tick
8. Health check goroutine uses ticker for precise intervals
9. Manual test: Monitor logs for 5 minutes, verify health checks appear every 60 seconds with accurate status
10. All code passes `go fmt`, `go vet`, and `staticcheck`
11. **(FIND-018)** The `config_loaded` entry reports the **effective** log level alongside the requested one, so an unrecognised `LOG_LEVEL` cannot advertise a verbosity that is not in force
12. **(FIND-017)** The Log Field Vocabulary lives in `docs/architecture/` as the durable contract for `component` / `event` / `operation`, current with the code and extended with this story's events

### Deviation: AC2/AC7 interpolated message — structured fields, not a formatted string

AC2 in the epic specifies the literal line `"Health check: MQTT=<connected|disconnected>, DB=<connected|disconnected>, Buffer=<n>/<capacity> messages"`, and AC7 `"Processed <n> messages in last 60s"`.

**Resolution: the values become structured attributes; `msg` stays a constant phrase.** Story 2.5 established, and QA verified, that `msg` is "a short lowercase-ish phrase, no interpolated values" and that every value an operator filters on is a field. Interpolating four values into the message string would make the one entry an operator most wants to aggregate the only entry they cannot — no log processor can chart `Buffer=850/1000` out of a sentence.

This is not a reinterpretation against the architecture; it is what the architecture already prescribes. The health-check example in `error-handling-strategy.md` logs exactly this way:

```go
app.logger.Info("Health check",
    "mqtt_connected", app.mqttClient.IsConnected(),
    "buffer_utilization", fmt.Sprintf("%d/%d", bufferLen, bufferCap),
    "dropped_messages_total", app.droppedMessages.Load(),
)
```

[Source: docs/architecture/error-handling-strategy.md#4-runtime-errors-resource-exhaustion-backpressure]

Two refinements on that snippet, deliberate:

- `buffer_used` and `buffer_capacity` are separate numeric fields rather than a `"850/1000"` string, for the same aggregation reason.
- `mqtt_status` / `db_status` carry the strings `connected` / `disconnected` rather than booleans, because AC2 names those two words as the vocabulary and a shared `connectionStatus` helper keeps MQTT and database phrased identically.

AC6's WARN keeps its wording close to the epic's, as a **separate entry** — severity is a property of an entry, and folding it into the INFO line would hide it from anyone filtering on `level=WARN`. **QA should not raise the wording divergence as a defect.** The PRD's AC2 and AC7 are to be amended to match, alongside the AC9/AC10 amendments already owed from story 2.5.

### Deviation: AC4 database status — last write *outcome*, not last write *recency*

AC4 in the epic says the database status is "verified by checking last successful write timestamp (no explicit Ping needed)".

**Taken literally, a recency rule is wrong for this application.** A recency test ("a write succeeded in the last 60 s ⇒ connected") reports `disconnected` for a perfectly healthy database whenever no MQTT message happened to arrive during the interval. On a home-automation broker, quiet minutes are normal, so the field would spend much of its life lying — and the one condition it exists to surface, a genuine outage, would be indistinguishable from an idle broker.

**Resolution: the status is the outcome of the most recent database interaction.** `connected` is seeded `true` by the startup `Ping` (which already proves reachability), set `false` by any failed `pool.Exec`, and set back `true` by any successful one. Recency is still reported, as its own field: `db_last_write_age_s`, with the sentinel `-1` when no write has succeeded since startup.

This honours AC4's actual constraint — **no `Ping` in the health check**, the status costs a single atomic load and never touches the network — while dropping only the part of its wording that would produce false alarms. Consequences the dev agent must respect:

- A stopped database with no traffic reports `db_status=connected` until a write is attempted. This is intentional and correct: nothing has observed a failure. `db_last_write_age_s` grows in the meantime and is the field that reveals a stale pipeline. Task 7's AC4 step publishes a message precisely to force an observation.
- A duplicate write (`ON CONFLICT DO NOTHING`, `RowsAffected() == 0`) counts as **both** a successful interaction and a processed message: the round-trip completed against a reachable database, and the message left the buffer for good. Store the timestamp and increment the counter once on `err == nil`, before the `RowsAffected()` branch — not separately in each arm.
- Do **not** add a `Ping` method to satisfy the word "verified". Do **not** reintroduce a health-check-driven reconnection: `insertWithRetry` already retries every message until it succeeds, and story 2.3.1 removed the redundant state machine on purpose.

| `mqtt` | `connecting`, `connected`, `connect_timeout`, `connect_failed`, `connection_lost`, `reconnecting`, `reconnect_failed`, `reconnected`, `reconnect_cancelled`, `disconnected`, `subscribing`, `subscribed`, `subscribe_failed`, `resubscribe_failed`, `message_received` |
| `database` | `connecting`, `connected`, `connect_failed`, `disconnected`, `write_success`, `write_failure`, `write_duplicate`, `topic_truncated`, `pool_stats` |

`unknown_log_level` is emitted from the `logger` package itself but tagged `component=main`, because it reports on the application's own configuration.

`operation` — **required on every ERROR or WARN entry that reports a failed *attempt***, naming what was being attempted: `load_config`, `connect`, `reconnect`, `subscribe`, `parse_dsn`, `ping`, `insert`.

Entries that report a *state* rather than a failed attempt carry **no** `operation`, whatever their level — there is no operation to name. These are `connection_lost` at ERROR, and `buffer_full`, `buffer_high`, `message_dropped`, `flush_timeout`, `write_duplicate`, `topic_truncated`, `unknown_log_level` at WARN. `connection_lost` is the single ERROR in that list and the reason the rule is not phrased "every ERROR carries an operation": the broker dropped the link on its own, no local call was attempted, so any `operation` value would be fabricated.

Domain fields by area:

| Area | Fields |
|------|--------|
| Message processing (`write_success` / `write_failure` / `write_duplicate`) | `topic`, `payload_size` (bytes), `duration_ms` |
| Health check (`health_check`) | `mqtt_status`, `db_status`, `db_last_write_age_s` (`-1` ⇒ no successful write since startup), `buffer_used`, `buffer_capacity`, `buffer_utilization_percent`, `processed_last_interval` |
| Buffer pressure (`buffer_high`) | `buffer_used`, `buffer_capacity`, `buffer_utilization_percent` |
| Startup / shutdown | `version`, `log_level`, `effective_log_level`, `buffer_size`, `buffer_capacity`, `interval_s`, `signal`, `count`, `buffered`, `failed_component` |

`failed_component` is deliberately not `component`: an entry naming a culprit is still emitted by `main`, and `component` must keep identifying the emitter.

### Performance

- One tick per minute against three atomic loads, a `len`, a `cap` and one INFO line. Negligible; no level guard is needed on the health entry, unlike the per-message DEBUG payload line.
- The counters added in Task 3 sit on the write path, one `Store` and one `Add` per message. Atomics on an uncontended cache line are on the order of nanoseconds against a database round-trip measured in milliseconds — do not add a mutex, and do not batch them.
- `len(msgChan)` and `cap(msgChan)` on a channel are O(1) and safe from any goroutine.
- **Use `sync/atomic`, not a `sync.Mutex`**, and do not guard the counters with the logger. Multiple goroutines are involved: the Paho callback produces, the DB writer consumes and writes, the health loop reads. Plain `int64` fields read across those goroutines would be a data race that `go test -race` and `go vet` would rightly flag.

SEC-001 holds.

### Performance Considerations

PASS. One tick per minute against three atomic loads, a `len` and a `cap`. The write path gains one
`Store` and one `Add` per successful insert, on an uncontended cache line, against a round-trip this
same function measured at 3–48 ms in the dev environment. `sync/atomic` as prescribed, no mutex, no
batching, and correctly no level guard on a once-a-minute INFO entry.

One accepted consequence, stated for the record: on an unbuffered channel (`BUFFER_SIZE=0`)
utilization is permanently `0`, so `buffer_high` can never fire. The zero guard is still right —
`NaN` once a minute forever is worse — and backpressure there remains visible through `buffer_full`.
