# Story 2.3: Implement PostgreSQL Automatic Reconnection

## Status

Done

## Story

**As a** system operator,
**I want** the application to automatically reconnect to PostgreSQL after connection loss,
**so that** database writes resume without manual intervention.

## Acceptance Criteria

1. `internal/database/client.go` wraps all database operations with connection health checks
2. On write failure due to connection error, log ERROR: "Database connection lost: <error>"
3. Implement reconnection loop with fixed 10-second retry interval
4. Reconnection attempts logged at INFO level: "Attempting database reconnection (attempt <n>)..."
5. Retry failed INSERT operations with 10-second interval until successful (connection verification implicit in successful INSERT)
6. On successful write after reconnection, log INFO: "Database reconnected successfully"
7. Failed messages during outage remain in channel buffer (not lost) and are retried after reconnection
8. Database writer goroutine continues processing buffered messages after reconnection
9. Manual test: Stop PostgreSQL container, publish MQTT messages (buffered), restart PostgreSQL, verify all buffered messages written after reconnection
10. All code passes `go fmt`, `go vet`, and `staticcheck`

### AC1 Interpretation

AC1 states `internal/database/client.go` wraps operations with "connection health checks." The pgx pool (`pgxpool.Pool`) already performs implicit health checking on every `Exec` call: it acquires a connection, and if all pool connections are stale/broken, it returns an error. `InsertMessage` returns that error to the caller. This is the "health check wrap" — no additional Ping or explicit reconnect is needed inside `internal/database/client.go`. The reconnection logic lives in the `dbWriterLoop` in `main.go`, which treats an INSERT error as a connection-lost signal.

### Current State of the DB Writer in `cmd/mqtt2bdd/main.go`

The anonymous goroutine (lines ~51–62) to be refactored:

```go
// DB writer goroutine: sole consumer of msgChan, exits when channel closed (story 2.4).
// On write failure, the message is retained and retried until success so no message is
// lost during a database outage. Story 2.3 will add detailed retry logging.
go func() {
    for msg := range msgChan {
        for {
            err := dbClient.InsertMessage(context.Background(), msg.Topic, msg.Timestamp, json.RawMessage(msg.Payload))
            if err == nil {
                break
            }
            // error already logged by InsertMessage; hold this message and retry after delay
            time.Sleep(defaultRetryIntervalOnDatabaseFailure)
        }
    }
}()
```

**Target `dbWriterLoop` implementation:**

```go
func dbWriterLoop(msgChan <-chan mqtt.Message, dbClient *database.Client, l *slog.Logger) {
    inReconnect := false
    for msg := range msgChan {
        attempt := 0
        for {
            err := dbClient.InsertMessage(context.Background(), msg.Topic, msg.Timestamp, json.RawMessage(msg.Payload))
            if err == nil {
                if inReconnect {
                    l.Info("Database reconnected successfully")
                    inReconnect = false
                }
                break
            }
            if !inReconnect {
                l.Error("Database connection lost", "error", err)
                inReconnect = true
            }
            attempt++
            l.Info("Attempting database reconnection", "attempt", attempt)
            time.Sleep(defaultRetryIntervalOnDatabaseFailure)
        }
    }
}
```

Launch site in `main()` becomes:
```go
go dbWriterLoop(msgChan, dbClient, l)
```

**Note on double-logging:** `InsertMessage` already logs `c.logger.Error("failed to insert message", ...)` on every failure. The new `l.Error("Database connection lost", ...)` only fires once (on the state transition from connected → reconnecting). Subsequent retries only emit the INFO "Attempting database reconnection" log. This means for the first failure you'll see two error lines (InsertMessage's detail + the state-transition line), which is intentional — they provide complementary context at different layers.

### Architecture: Naming and Constants

`defaultRetryIntervalOnDatabaseFailure = 10 * time.Second` is already defined in `cmd/mqtt2bdd/main.go`. Re-use it for the `time.Sleep` inside `dbWriterLoop`. Do NOT add a new constant.

### Architecture: Concurrency Rules

- The `dbWriterLoop` goroutine must have a clear exit condition. It exits when `msgChan` is closed (the `for msg := range msgChan` loop terminates on channel close). This is the correct exit path, as `main.go` will close `msgChan` during graceful shutdown (story 2.4).
- The goroutine owns the read end of `msgChan` exclusively — no other code reads from it.

[Source: architecture/coding-standards.md#concurrency]
