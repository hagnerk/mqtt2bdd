13. **(PO-mandated, carried from Story 3.1 / FIND-025)** `docker-compose.prod.yml` sets `stop_grace_period: 30s` on the application service, matching `defaultShutdownTimeout` in `cmd/mqtt2bdd/main.go:25`. Docker's default grace is 10 s: with a non-empty buffer during a database outage, `insertWithRetry` can legitimately occupy the full 30 s drain, and a plain `docker stop` would SIGKILL the process at t+10 s — losing buffered messages, yielding exit 137, and emitting neither `flush_timeout` nor `shutdown_complete`. ### Deviation: AC6 — `.env.prod.example` is a template, not an `env_file`

AC6 says the service is "configured with environment variables via `.env.prod.example` file". Read
literally that would mean `env_file: .env.prod.example` in the compose file, which would be wrong twice
over: the example file carries the placeholder `<replace_with_strong_password>`, so the stack would start
with a literal placeholder as its password; and the real file is `.env.prod`, which is never committed.

**Resolution: `.env.prod.example` is the committed template (AC10's subject); the operator copies it to
`.env.prod` and supplies it with `--env-file .env.prod` on every Compose command.** That is exactly what
`docs/architecture/infrastructure-and-deployment.md#environments` already prescribes:

```bash
cp .env.prod.example .env.prod
nano .env.prod  # Edit POSTGRES_PASSWORD and other settings
```

**One mechanism, not two.** `--env-file` feeds Compose's **variable interpolation** — the `${VAR}` forms in
the YAML. `env_file:` inside a service feeds the **container's environment** directly and is a different
channel that `--env-file` does not populate. Mixing them means a variable can be set in one and unset in
the other, which is a genuinely confusing failure. This file uses interpolation only, and every value the
application needs is spelled out in an explicit `environment:` block — the same shape the architecture's
own production snippet uses. The cost is that **every** Compose command against this file needs
`--env-file .env.prod`, including `ps`, `logs` and `exec`. Every command in The Manual Test below carries it.

### Deviation: AC8 — what a health check can honestly mean for a pure consumer

AC8 requires health checks for all three services. Two of them are routine. The third needed a decision,
and this section takes it.

**The problem.** `mqtt2bdd` exposes **no HTTP endpoint and no port**. The image sets no `EXPOSE`, its
`.Config.ExposedPorts` is empty, and Story 3.1 deliberately added no `HEALTHCHECK` to the Dockerfile
because "there is no probe to run in an image whose health signal is a log line". What the image *does*
give us is busybox (304 applets, `/bin/sh` among them) — established as fact by the PO when closing
FIND-024, specifically so this story could reason about it.

**Options considered, and why each was accepted or rejected:**

| Candidate probe | Verdict |
| --------------- | ------- |
| `pgrep -f mqtt2bdd` / `pidof mqtt2bdd` — process liveness | **Rejected as the sole check.** Near-tautological: the binary is PID 1, so if the process dies the container dies and Docker never runs the probe. It can only ever report `healthy`. A check that cannot fail is worse than none — it puts a green light next to a service nobody is actually watching |
| `nc -z $POSTGRES_HOST $POSTGRES_PORT && nc -z $MQTT_BROKER $MQTT_PORT` — open fresh TCP connections to both dependencies | **Rejected.** It proves the *network path* is open, not that the application is using it — a wedged app scores healthy. It also opens and abandons a TCP connection to the broker every interval, which Mosquitto logs as a socket error, and to PostgreSQL, which logs `incomplete startup packet`. A probe that manufactures error lines in two other services' logs is a bad trade |
| `netstat` on **both** `:1883` and `:5432` — read the app's own socket table | **Rejected.** The pgx pool runs `MinConns=1, MaxConns=5, MaxConnIdleTime=5m` (`internal/database/client.go:18-20,72-74`) and the pool's own background health check refills to `MinConns` only once a minute, so there are legitimate windows with zero established PostgreSQL connections. Observed while drafting: two `TIME_WAIT` entries to `:5432` alongside the established ones. A check that flaps on a healthy application is the same false-alarm failure the PO rejected for AC4 of story 2.6 |
| **`netstat` on the broker connection only** — chosen | **Accepted.** See below |

**The decision: the health check asserts that the application still holds an ESTABLISHED TCP connection to
the MQTT broker on `$MQTT_PORT`, by reading its own socket table.**

```yaml
test: ['CMD-SHELL', 'netstat -tn | grep -qE "[0-9.]+:$$MQTT_PORT[[:space:]]+ESTABLISHED"']
interval: 30s
timeout: 5s
retries: 3
start_period: 30s
```

Why this one:

- **It is the failure that matters.** No broker link means no data reaches the pipeline at all. Everything downstream — the buffer, the writer, the retry loop — is designed to survive a database outage; nothing survives a broker outage. The MQTT connection is also genuinely persistent: `internal/mqtt/client.go:58` sets `opts.SetAutoReconnect(false)` because the project runs its own reconnect logic, so the socket is either up or the app is in a reconnect loop. There is no idle-churn equivalent of the pgx pool.
- **It opens no connection of its own**, so it adds no line to the broker's log and cannot be fooled by a probe that succeeds against a service the application is not actually talking to. It reads `/proc/net/tcp`, which is world-readable — verified working as UID 65534 under `read_only: true`.
- **It is fast and it does not flap.** Measured at well under the 5 s timeout; busybox `netstat` on a five-socket table is microseconds.
- **`start_period: 30s`** covers startup. The app connects to both dependencies inside `defaultConnectTimeout` (10 s each) or exits with `startup_aborted`, and `depends_on: service_healthy` means it does not even start until the broker is up. Observed startup to `startup_complete`: **6 ms**.

**Verified, not asserted.** While drafting this story the production image was rebuilt and run against the
dev network as `--user 65534:65534 --read-only --tmpfs /tmp`, and the probe command was executed inside it:

```text
$ netstat -tn
Proto Recv-Q Send-Q Local Address           Foreign Address         State
tcp        0      0 192.168.166.5:36342     192.168.166.2:1883      ESTABLISHED
tcp        0      0 192.168.166.5:52134     192.168.166.3:5432      TIME_WAIT
tcp        0      0 192.168.166.5:52154     192.168.166.3:5432      ESTABLISHED
$ netstat -tn | grep -qE "[0-9.]+:1883[[:space:]]+ESTABLISHED"; echo $?
0
```

The container and the probe image were removed afterwards; nothing was left on the host.

**Re-verified by the PO on 2026-07-25, independently of the SM.** The image was rebuilt
(`docker build --build-arg VERSION=po-probe`, measuring 18,554,844 bytes — the same figure Story 3.1
recorded, which is what makes AC16's baseline real rather than inherited), run on the dev network as
`--user 65534:65534 --read-only --tmpfs /tmp`, and probed from inside. `id` → `uid=65534(nobody)`;
`ReadonlyRootfs=true`; `netstat -tn` printed one `ESTABLISHED` to `:1883` alongside **both** `ESTABLISHED`
and `TIME_WAIT` entries to `:5432` — which is the observation that justifies rejecting a PostgreSQL-side
probe, reproduced independently; the probe command as the container's own shell runs it returned **exit 0**
with `MQTT_PORT` expanded to `1883`; `docker stop` produced `flush_complete` → `shutdown_complete` and
**exit 0**. `pg_isready` and the `mosquitto_sub` `$SYS` probe were each executed against the real images and
each returned exit 0, the latter in 0.098 s wall. The container and image were removed; the dev stack was
untouched and no `sensor_metrics` row was created. **The claim is true. The probe is accepted.**

**Two honest limitations, stated rather than glossed:**

1. **It cannot detect FIND-010.** If a re-subscription fails after a reconnect, the TCP connection stays established and this probe stays green while the application silently receives nothing. That is precisely why FIND-010 is an explicit AC on **Story 3.3**, whose integration harness can prove a retry. Do not claim in the Dev Agent Record that this check covers it.
2. **Docker does not restart an unhealthy container.** `restart: unless-stopped` reacts to *exit*, not to *unhealthy*; only Swarm acts on health. So the practical value of this probe is an honest status in `docker compose ps` and a signal any external watchdog can read — not self-healing. Say so, do not oversell it.

**PO ruling on those two limitations: acceptable — a probe honest about what it cannot see is worth more
than one that is not — but they may not live here alone.** Dev Notes is read once, by a Dev agent, before
implementation; an operator reads the compose file and the README. Both limitations are therefore now
stated as a comment beside the probe in the reference `docker-compose.prod.yml`, and limitation 2 is stated
in one sentence in the README section (Task 6). Neither may be dropped as verbosity.

**The other two probes**, both executed against the real images while drafting:

- **PostgreSQL:** `pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB`. `pg_isready` ships at `/usr/local/bin/pg_isready` in `postgres:15-alpine`. `interval: 10s, timeout: 5s, retries: 5, start_period: 30s` — tighter than the others because `depends_on: condition: service_healthy` gates the whole stack on it, and a first-boot initdb plus the `01-schema.sql` run takes a few seconds.
- **Mosquitto:** `mosquitto_sub -h 127.0.0.1 -p 1883 -t '$$SYS/broker/uptime' -C 1 -W 3 -i healthcheck`. Mosquitto publishes `$SYS` topics **retained**, so a fresh subscriber gets the value immediately — measured at **0.04 s**, exit 0, on a broker that had just started. It proves the broker accepts a connection *and* serves a message, and it publishes nothing, which matters: `mqtt2bdd` subscribes to `#`, so a `mosquitto_pub`-based probe would write a row into `sensor_metrics` every interval. `interval: 30s, timeout: 5s, retries: 3, start_period: 30s`.
  - Note the `$$` in both: Compose collapses `$$` to a literal `$`, so `$$SYS` reaches the shell as `$SYS` and `$$POSTGRES_USER` reaches it as `$POSTGRES_USER` for the container's own shell to expand. Writing a single `$` makes Compose interpolate it at parse time and the probe silently degrades.
  - The probe connects to the broker every 30 s, which Mosquitto logs. That is the accepted cost of a real health check; the `logging:` block caps the log at 10 MB × 3 files. If it proves too noisy in practice, the lever is `interval:`, not removing the check.

### Deviation: AC9 — `restart: unless-stopped` and what `depends_on` does not do

AC9 says "Restart policy set to `unless-stopped` for production resilience". It does not say on which
service; it is applied to **all three**, which is what "for production resilience" means for a stack meant
to survive a host reboot.

**`restart:` and `depends_on:` solve different problems and neither substitutes for the other:**

- `depends_on: condition: service_healthy` is **startup ordering only**. It delays `mqtt2bdd` until PostgreSQL and Mosquitto report healthy, which is exactly what the application needs — `config.LoadConfig` succeeds without them but `mqttClient.Connect` and `dbClient.Connect` each get `defaultConnectTimeout` (10 s) before `startup_aborted` and `os.Exit(1)`.
- It does **nothing at run time**. If PostgreSQL restarts an hour later, Compose does not restart `mqtt2bdd` and does not need to: stories 2.2 and 2.3 built reconnection, and `insertWithRetry` holds each message and retries every 10 s until the write succeeds. The buffer is what absorbs the outage. Do not add anything that restarts the app on a dependency blip — it would throw away the buffered messages the design exists to protect.
- `restart: unless-stopped` covers the residual case: the app exits non-zero anyway (a genuinely unreachable dependency at boot, a panic), and Docker brings it back. Combined with `depends_on`, a restart loop at first boot is unlikely; if one happens it is visible in `docker compose ps` and the logs, which is the right outcome.
- `unless-stopped` rather than `always` is deliberate and is what the AC names: a container the operator stopped by hand stays stopped across a daemon restart.

### Service Names Versus Container Names

AC1 names the **services** (`postgres`, `mosquitto`, `mqtt2bdd`); AC5 names the **containers**
(`mqtt2bdd-prod-postgres`, `mqtt2bdd-prod-mosquitto`, `mqtt2bdd-prod-app`). Both are satisfied at once, and
the asymmetry is deliberate — note especially that the application's service is `mqtt2bdd` while its
container is `mqtt2bdd-prod-**app**`:

```yaml
services:
  mqtt2bdd:                            # AC1: the service name
    container_name: mqtt2bdd-prod-app  # AC5: the container name
```

`dev/docker-compose.yml` uses exactly this pattern (`postgres` → `mqtt2bdd-dev-postgres`), so the production
file is recognisably its sibling. Practical consequences the Dev agent must respect:

- `docker compose exec` addresses **services**: `docker compose -f docker-compose.prod.yml --env-file .env.prod exec mosquitto mosquitto_pub ...`.
- `docker logs`, `docker exec` and `docker inspect` address **containers**: `docker logs mqtt2bdd-prod-app`.
- Docker's internal DNS resolves **both**, which is why `POSTGRES_HOST=mqtt2bdd-prod-postgres` works. Container names are used in `.env.prod.example` rather than service names because that is the convention `dev/.env.example` already set, and because they are unambiguous when two stacks are up at once.

### Network, Volumes and the Compose Name Prefix

Compose prefixes the project name onto every network and volume it declares. `dev/docker-compose.yml`
declares `mqtt2bdd-dev-network` and Docker creates `mqtt2bdd-dev_mqtt2bdd-dev-network` — a stumble Story 3.1
hit during its smoke test. Avoid it by declaring the real name explicitly:

```yaml
networks:
  mqtt2bdd-prod-network:
    name: mqtt2bdd-prod-network      # explicit: suppresses the "mqtt2bdd-prod_" prefix
    driver: bridge

volumes:
  mqtt2bdd-prod-pgdata:
    name: mqtt2bdd-prod-pgdata
  mqtt2bdd-prod-mosquitto-data:
    name: mqtt2bdd-prod-mosquitto-data
```

The naming follows the `mqtt2bdd-prod-` convention AC5 sets for containers, extended to every named object
in the stack, so `docker network ls` and `docker volume ls` group the whole stack under one prefix and
nothing collides with `mqtt2bdd-dev-*`. AC7's "dedicated Docker network" is satisfied by the single bridge
network all three services join; no service uses the default network and none uses host networking.

### Ports

The dev stack binds host **5432** and **1883** (`dev/docker-compose.yml:11,21`) and stays up throughout
Task 8, so a production stack with the same bindings cannot start. Three options were considered:

1. **No host bindings at all**, as the architecture's *test* stack does. Rejected: production genuinely needs them. Home-automation devices publish to the broker over the LAN and Grafana queries PostgreSQL from off-host; a production stack reachable only from inside its own bridge network is not deployable.
2. **Fixed alternative ports** (15432, 11883). Rejected: it makes the *production* defaults unnatural in order to accommodate a one-off test on the maintainer's laptop.
3. **Parameterised host bindings with the natural defaults** — chosen:

```yaml
ports:
  - "${POSTGRES_HOST_PORT:-5432}:5432"
  - "${MQTT_HOST_PORT:-1883}:1883"
```

A real deployment sets nothing and gets 5432 and 1883. Task 8 sets `POSTGRES_HOST_PORT=15432` and
`MQTT_HOST_PORT=11883` in its throwaway `.env.prod` and both stacks coexist. **The container-side ports
never change** — the app reaches PostgreSQL on 5432 and the broker on 1883 across the bridge network
regardless of the host binding, which is why `POSTGRES_PORT` and `MQTT_PORT` (the variables the
*application* reads) are separate variables from `POSTGRES_HOST_PORT` and `MQTT_HOST_PORT` (the variables
*Compose* reads). Conflating them is the single most likely misconfiguration of this file, and it is why
`.env.prod.example` splits them into two labelled sections with a warning on each.

### Non-Root and Read-Only at Runtime

`docs/architecture/security.md#container-security` prescribes three hardening measures; the image already
delivers the first. The compose file adds the other two and restates the first:

```yaml
    user: "65534:65534"   # nobody:nogroup — agrees with USER nobody in the image
    read_only: true
    tmpfs:
      - /tmp
```

- **`user:` is restated deliberately, not redundantly.** The image sets `USER nobody` (UID/GID 65534), so the container is already non-root without it. `security.md#container-security` prescribes the compose key as well, and the PO's AC10 ruling in Story 3.1 kept both on the explicit grounds that they "agree numerically, so this is defence in depth rather than a duplicated decision". Restating it also makes the identity visible in the file an operator actually reads.
- **`read_only: true` was verified, not assumed.** While drafting, the production image was run with `--user 65534:65534 --read-only --tmpfs /tmp` against the dev stack. It reached `startup_complete` in 6 ms, connected to both dependencies, held its subscription, and shut down cleanly on `docker stop` with `flush_complete` → `shutdown_complete` and **exit code 0**. The application writes nothing to disk — logs go to stdout, no state files, and Story 3.1's inspection confirmed the image declares no `VOLUME`.
- **`tmpfs: /tmp`** comes from the same architecture snippet ("required by some Go runtime internals"). It was not observed to be *needed* in the verification above, but it costs nothing, it is what the architecture prescribes, and removing it would be a change this story has no reason to make.
- **Apply all three to the `mqtt2bdd` service only.** PostgreSQL writes to `/var/lib/postgresql/data`, `/var/run/postgresql` and `/tmp`; Mosquitto writes to `/mosquitto/data`. `read_only: true` on either breaks it.
- **If the stack fails to start with `read_only: true`** — it did not in the verification above, so this should not arise — diagnose before removing it: `docker logs mqtt2bdd-prod-app` will name the path it could not write. Adding that path as a second `tmpfs:` entry is the fix; dropping `read_only` is a last resort and must be recorded in the Dev Agent Record with the log line that justified it.

### How the Version Reaches the Build

Four hops, and every one has to line up or the image ships labelled `dev`:

1. `VERSION=0.1.0` is a line in `.env.prod`.
2. `--env-file .env.prod` makes Compose read it for **interpolation**.
3. `args: VERSION: ${VERSION:-dev}` passes it into the build as a build arg, where the Dockerfile's `ARG VERSION=dev` (declared in *both* stages) receives it.
4. `-ldflags "-X main.Version=${VERSION}"` writes it into `main.Version`, and the runtime stage's `LABEL org.opencontainers.image.version` records it.

`image: mqtt2bdd:${VERSION:-dev}` tags the result so it is inspectable by name (AC16 needs that) and so a
rebuild replaces the tag rather than leaving a dangling image. Verify at Task 8 by reading the version back
two ways — `docker logs mqtt2bdd-prod-app | head -1` must show `version=0.1.0`, not `version=dev`, and
`docker image inspect mqtt2bdd:0.1.0 --format '{{index .Config.Labels "org.opencontainers.image.version"}}'`
must print `0.1.0`, not an empty string.

### Architecture-Prescribed Blocks (AC19)

Two blocks in the reference file are prescribed by `docs/architecture/infrastructure-and-deployment.md#environments`
for this exact file. They were flagged for the PO to strike at validation. **The PO kept them and promoted
them to AC19.** The reasoning is the project's own: architecture-prescribed content omitted from the very
file the architecture describes recreates the documentation gap AC18 exists to close — and a requirement
that lives only as Dev Notes prose is precisely the FIND-017 failure mode, the same one that turned FIND-025
into AC13 rather than a note. An AC is what a QA gate can trace; prose is not.

- **`logging:` (json-file, `max-size: 10m`, `max-file: 3`)** — applied to all three services. Unbounded container logs on a home server that runs for months is a real failure mode, and the broker logs a connection from the Mosquitto health check every 30 s, which makes it slightly more real.
- **`deploy.resources`** (limits 0.5 CPU / 256 M, reservations 0.25 CPU / 128 M) — applied to the `mqtt2bdd` service only, which is what the architecture specifies. **`limits` are applied by Compose v2+ on a plain `up` and Task 8 verifies them** (`NanoCpus` = 500000000, `Memory` = 268435456). **`reservations` are advisory outside Swarm** — they are kept because the architecture prescribes them and removing them would be a change this story has no reason to make, but nothing in the Dev Agent Record may claim they were enforced. If the application is ever OOM-killed at 256 M the fix is to raise the limit knowingly, which is better than discovering there was never one.

```yaml

#   docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
# Every command against this file needs --env-file: the values below arrive by

      - mqtt2bdd-prod-network

      start_period: 30s

    restart: unless-stopped                     # (AC9)

      - ./prod/mosquitto/mosquitto.conf:/mosquitto/config/mosquitto.conf:ro
      - mqtt2bdd-prod-mosquitto-data:/mosquitto/data

      - "${MQTT_HOST_PORT:-1883}:1883"

      - mqtt2bdd-prod-network

      # $SYS topics are retained, so this returns immediately (measured: 0.04 s) and
      # publishes nothing — a mosquitto_pub probe would write a row to sensor_metrics
      # on every interval, because the application subscribes to '#'. (AC8)
      test: ["CMD-SHELL", "mosquitto_sub -h 127.0.0.1 -p 1883 -t '$$SYS/broker/uptime' -C 1 -W 3 -i healthcheck"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

  mqtt2bdd:
    build:
      context: .
      dockerfile: Dockerfile                    # the production Dockerfile, not dev/Dockerfile.dev
      args:
        VERSION: ${VERSION:-dev}                # reaches main.Version via -ldflags
    image: mqtt2bdd:${VERSION:-dev}             # tag the result so it is inspectable by name
    container_name: mqtt2bdd-prod-app           # (AC5)
    restart: unless-stopped                     # (AC9)
    depends_on:
      # Startup ordering only. Runtime outages are handled by the application's own
      # reconnect logic and its buffer — nothing here restarts the app on a blip.
      postgres:
        condition: service_healthy
      mosquitto:
        condition: service_healthy
    environment:
      # Every value the application reads, from internal/config/config.go.
      MQTT_BROKER: ${MQTT_BROKER:-mqtt2bdd-prod-mosquitto}
      MQTT_PORT: ${MQTT_PORT:-1883}
      MQTT_USERNAME: ${MQTT_USERNAME:-}
      MQTT_PASSWORD: ${MQTT_PASSWORD:-}
      POSTGRES_HOST: ${POSTGRES_HOST:-mqtt2bdd-prod-postgres}
      POSTGRES_PORT: ${POSTGRES_PORT:-5432}
      POSTGRES_DB: ${POSTGRES_DB:-mqtt2bdd}
      POSTGRES_USER: ${POSTGRES_USER:-mqtt2bdd}

          cpus: '0.5'
          memory: 256M
        reservations:
          cpus: '0.25'
          memory: 128M

networks:

  mqtt2bdd-prod-network:
    name: mqtt2bdd-prod-network
    driver: bridge

volumes:
  mqtt2bdd-prod-pgdata:
    name: mqtt2bdd-prod-pgdata
  mqtt2bdd-prod-mosquitto-data:
    name: mqtt2bdd-prod-mosquitto-data
```

```bash
#
# Copy this file to .env.prod and fill in the values:
#     cp .env.prod.example .env.prod
#
# .env.prod is NEVER committed — it holds a real password and is gitignored.

# name for the self-contained stack; set it to a hostname or IP to point the
# application at a broker you already run. Required, no default.
MQTT_BROKER=mqtt2bdd-prod-mosquitto

# Broker port INSIDE the Docker network. Leave at 1883 even if you changed
# MQTT_HOST_PORT — the two are different things. Required, must be an integer.
MQTT_PORT=1883

MQTT_USERNAME=

POSTGRES_PORT=5432

# Required, no default.
POSTGRES_DB=mqtt2bdd

# Database user. Created on first startup and owns the sensor_metrics table.

POSTGRES_USER=mqtt2bdd
```

### `prod/mosquitto/mosquitto.conf`

```conf

# The development broker (dev/mosquitto/mosquitto.conf) is the same two directives
# without persistence; everything below is what production adds.

# Listen on the standard MQTT port on every interface in the container.
listener 1883

#

# mqtt2bdd-prod-mosquitto-data volume rather than lost with the container.
persistence true
persistence_location /mosquitto/data/

# Log to stdout so `docker logs mqtt2bdd-prod-mosquitto` is the single place to look,
# and so the container's json-file log rotation bounds broker logs too.
log_dest stdout
```

**`allow_anonymous true` — flagged for the PO, and ACCEPTED at validation on 2026-07-25.** It matches the
dev broker, it matches the threat model ("private home network, no public internet exposure"; "external
network attacks (no public endpoint)" and "authentication/authorisation bypass" both explicitly out of
scope), and it matches what `docs/architecture/infrastructure-and-deployment.md#environments` says of the
production broker: "Configured with anonymous access or authentication" — verified in the document, not
paraphrased. The alternative — shipping a password file — would put a second credential in the repository,
which is a SEC-001 decision and needs a story of its own.

**Two conditions the PO attached, both already reflected above and in the README section:**

1. **The consequence is spelled out where the setting is, and again in the README.** This file publishes a
   broker port on the host by default. "Anonymous" is a one-word setting whose blast radius is that anyone
   who reaches the port can write to `sensor_metrics`. Recording it as "consistent with the threat model"
   and stopping there is how a threat model quietly becomes an excuse.
2. **The escape hatch is real and was verified, not assumed.** The *application* half of the credential
   plumbing already ships: `internal/config/config.go:83-84` reads `MQTT_USERNAME` and `MQTT_PASSWORD`, and
   `internal/mqtt/client.go:53-55` applies them through `SetUsername`/`SetPassword` when the username is
   non-empty. `.env.prod.example` already carries both variables. Nothing in this story is needed to make
   authentication *possible*.

**Who owns it if authentication is ever required:** not this story and not 3.3. What is missing is the
**broker** half — a `mosquitto_passwd` file, `password_file`, `allow_anonymous false`, and a decision about
where that credential lives given SEC-001. That is a new, unapproved story; it is recorded as a deferral in
Carry-Forward Findings for the project owner, and it must **not** be improvised inside this one.

```sql
-- MQTT2BDD production database schema.
-- Executed once by the postgres container, on an empty data directory only.
-- Matches docs/architecture/database-schema.md#table-sensor_metrics.

CREATE TABLE IF NOT EXISTS sensor_metrics (
    id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sensor  VARCHAR(255) NOT NULL,
    date    TIMESTAMP    NOT NULL,
    metrics JSONB        NOT NULL,
    CONSTRAINT unique_sensor_date UNIQUE (sensor, date)
);

-- Composite index for the time-range queries Grafana issues.
CREATE INDEX IF NOT EXISTS idx_sensor_metrics_sensor_date
    ON sensor_metrics (sensor, date DESC);

-- GIN index so filters on JSON fields inside metrics do not scan the table.
CREATE INDEX IF NOT EXISTS idx_sensor_metrics_metrics
    ON sensor_metrics USING GIN (metrics);
```

**Two things to know about `/docker-entrypoint-initdb.d`:** it runs **only** when the data directory is
empty, so re-running `up` against an existing `mqtt2bdd-prod-pgdata` volume silently skips it (which is
why Task 8's cleanup uses `down -v`); and it runs as the superuser, which here is `POSTGRES_USER`
(`mqtt2bdd`), so the table is owned by the application user. No `GRANT` is needed and none is written —
the least-privilege split `security.md`'s checklist describes needs a second database role and is not in
this story's scope.

````markdown
## Production Deployment

The production stack (`docker-compose.prod.yml`) runs three containers — the application,

```

`--build` compiles the binary from the production `Dockerfile` and injects `VERSION`

docker compose -f docker-compose.prod.yml --env-file .env.prod ps
docker logs mqtt2bdd-prod-app --tail 20
```

All three services report `healthy` once started. The application logs
`event=startup_complete version=…` when it has connected to both the broker and the
database and subscribed to `#`.

The application's health check reports whether it still holds a connection to the broker.
It is a **status signal, not self-healing**: Docker restarts a container that *exits*, not
one that reports `unhealthy`. Watch `docker compose ps`, or point an external watchdog at it.

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod down
```

`down` stops the stack and keeps the data volumes. Add `-v` to delete the PostgreSQL
data and the broker's persistence store as well — that is destructive.

and `MQTT_BROKER` in `.env.prod` to their hostnames and start only the application:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build mqtt2bdd

The bundled broker accepts **anonymous** connections: anything that can reach the published
MQTT port can publish to any topic, and — because the application subscribes to `#` — write
rows into the database. That is deliberate and matches this project's threat model (a private
````

- **`up` hangs at "waiting for postgres to be healthy".** Read `docker logs mqtt2bdd-prod-postgres`.
