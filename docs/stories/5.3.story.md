# Story 5.3: Exclude Topics from Persistence

## Status

Draft

## Story

**As an** operator,
**I want** to list MQTT topic filters whose messages are not stored,
**so that** configuration traffic such as `zigbee2mqtt/bridge/#` does not fill `sensor_metrics`.

## Acceptance Criteria

> **ACs 1–10 are copied verbatim from Epic 5 in `docs/prd.md:933-950`.** None is reworded and none is added. Where an AC leaves a detail open, the answer is recorded in Dev Notes → SM Clarifications, with its source or its reasoning. Release target: **v1.1.0** (new configuration variable). It builds on Stories 5.1 and 5.2 (both Done, shipped as v1.0.1) but touches none of their code.

1. A new optional environment variable `MQTT_EXCLUDE_TOPICS` holds a comma-separated list of MQTT topic filters. Surrounding whitespace is trimmed, empty entries are ignored, and an unset or empty value excludes nothing
2. Each filter is validated at startup against MQTT 3.1.1 §4.7: `#` only as a whole, final level; `+` only as a whole level; no NUL character. An invalid filter aborts startup with `event=config_load_failed`, naming the offending filter
3. Matching follows MQTT semantics: `+` matches exactly one level; `#` matches the parent level and any number of child levels (`a/#` matches `a`); empty levels are significant; matching is case-sensitive; a topic starting with `$` is not matched by a filter starting with a wildcard
4. An excluded message is dropped in the reception handler before it reaches the buffer, and is not counted by `processed_last_interval`
5. Each exclusion is logged at DEBUG with `event=message_excluded`, `topic` and the matching `filter`; nothing is logged per message at INFO
6. The `config_loaded` entry reports the parsed list as `exclude_topics`
7. The subscription stays `#`: MQTT has no negative subscription, so excluded payloads still cross the network. The README states this
8. `MQTT_EXCLUDE_TOPICS` is documented in the README configuration table (with `zigbee2mqtt/bridge/#` as the example), in `.env.prod.example`, and passed through in `docker-compose.prod.yml`. `docs/architecture/components.md` and `docs/architecture/logging-standards.md` are updated
9. Unit tests cover filter validation, the matching rules above including the examples of MQTT 3.1.1 §4.7, and configuration parsing. An integration test shows that a message on an excluded topic is absent and a message on another topic is stored
10. Verification passes as in Story 5.1, AC12

### Matching Algorithm

`MatchTopic(filter, topic string) bool`, guidance for an allocation-free implementation (the behaviour, not this exact code, is the contract):

```
if topic starts with "$" and filter starts with "+" or "#":  return false      // §4.7.2
loop:
    fLevel, fRest, fMore := strings.Cut(filter, "/")
    if fLevel == "#":                return true        // this level and everything below, including nothing
    tLevel, tRest, tMore := strings.Cut(topic, "/")
    if fLevel != "+" && fLevel != tLevel:  return false  // byte comparison: case-sensitive, empty level significant
    if !fMore && !tMore:             return true         // both exhausted together
    if !fMore:                       return false        // topic has more levels than the filter
    if !tMore:                       return fRest == "#" // "a/#" matches "a"; "a/+" does not match "a"
    filter, topic = fRest, tRest
```

Walk-throughs, all in the Test Matrix: `sport/+` vs `sport` → false (last line); `sport/+` vs `sport/` → true (the empty level matches `+`); `+` vs `/finance` → false (topic has two levels); `/+` vs `/finance` → true; `a/#` vs `a/` → true. A topic name never contains `+` or `#` (a compliant broker never delivers one), so the topic side needs no wildcard handling. [Source: MQTT 3.1.1 (OASIS Standard, 2014) §4.7.1 Topic wildcards, §4.7.2 Topics beginning with $, §4.7.3 Topic semantic and usage]

### SM Clarifications

Where the ACs leave a detail open, these answers apply.

- **C1 — Placement: validation in `internal/config`, matching in `internal/mqtt`, the decision in `main`.** AC2 makes an invalid filter a configuration error (`config_load_failed`), and `components.md` gives validation to the Configuration Manager, so `LoadConfig` must validate. The check cannot be delegated to `internal/mqtt`, because `internal/mqtt` already imports `internal/config` and the reverse import would be a cycle. Matching is MQTT protocol semantics used on received messages, so it belongs with the MQTT client; `main` already imports `internal/mqtt`. `logging-standards.md` lists `message_excluded` under `main`, which places the drop in `main`'s handler (AC4: "in the reception handler"). No new package: `source-tree.md` and `components.md` name four internal packages, and a fifth for two functions is not justified. The two functions share the grammar of §4.7 but check different things (well-formedness vs matching), so the split duplicates no rule.
- **C2 — "Excludes nothing" is a `nil` slice.** Unset, empty, blank-only and separator-only values all give `ExcludeTopics == nil`. One representation keeps `reflect.DeepEqual` in tests unambiguous (`nil` and `[]string{}` are not deep-equal) and lets the existing `config_test.go` rows stay as they are.
- **C3 — `exclude_topics` is rendered as the comma-joined list.** Passing the slice to slog renders `exclude_topics="[a/# b c]"`, where a space inside a filter (legal in MQTT) cannot be told apart from the separator (verified in `go-dev`). A filter can never contain a comma (it is the input separator), so `strings.Join(…, ",")` is unambiguous, mirrors the variable's own syntax, and shows the list after trimming and empty-entry removal, which is what "the parsed list" means. An empty list renders as `exclude_topics=""`.
- **C4 — Order and duplicates.** Filters are kept in configured order, duplicates included; `excludingFilter` reports the first match. Deduplicating would add code for no behavioural difference, and "first in the order you wrote them" is the simplest rule to document.
- **C5 — `message_received` still precedes `message_excluded`.** The DEBUG `message_received` entry (with the payload body) is logged inside `internal/mqtt` before the handler runs, so at DEBUG an excluded message still appears there, followed by `message_excluded`. Moving the check into `internal/mqtt` would contradict C1 and `logging-standards.md`. At INFO neither line exists. Operators who exclude a large topic to keep DEBUG readable should know this; the README Troubleshooting entry is enough.
- **C6 — The check is the handler's first statement.** An excluded message must never be timestamped, must never wait on a full buffer, and must never produce `buffer_full` or `message_dropped`. Checking before the send guarantees all three.
- **C7 — Validation covers exactly AC2's three rules.** Not checked: UTF-8 well-formedness and the 65,535-byte length limit of §1.5.3 — the AC lists its rules, and a filter violating them simply never matches a received topic. A filter that matches everything (`#`) is valid and accepted without a warning; `config_loaded` shows it. A `$SYS/#` filter is valid too, but never matches anything, because a compliant broker does not deliver `$` topics to a `#` subscription (§4.7.2).
- **C8 — The `$` rule is unit-tested only.** For the reason in C7, the application never receives a `$` topic, so no integration test can exercise it. `MatchTopic` still implements it, because AC3 requires MQTT semantics and the function must not depend on the subscription it happens to be used with.
- **C9 — The NUL rule is tested white-box.** `os.Setenv` refuses a value containing a NUL byte (`setenv: invalid argument`, verified in `go-dev`), so `LoadConfig` can never see one through the real environment. `validateTopicFilter` still checks it (AC2) and `topics_test.go` covers it directly.
- **C10 — Trimming uses `strings.TrimSpace`.** A filter with meaningful leading or trailing spaces therefore cannot be expressed; inner spaces are kept. This is what AC1 asks for and is documented in the README row.
- **C11 — `dev/.env.example` gets the variable too**, empty. AC8 does not list it, but the README presents `dev/.env.example` and `.env.prod.example` as the two ready-to-copy templates of the complete variable list, and the dev stack reads `.env` through `env_file`. No change to `dev/docker-compose.yml` is needed (`env_file` passes every variable).
- **C12 — `.env.prod.example` ships the variable empty**, with `zigbee2mqtt/bridge/#` as a commented example: a copied template must keep v1.0.0 behaviour (Epic 5 compatibility). The README table carries the example value AC8 requires.
- **C13 — No counter and no health field for exclusions.** No AC asks for one; exclusions are configuration, not loss (`core-workflows.md` → Error Handling Summary: "Data Loss? No (excluded by configuration)").
