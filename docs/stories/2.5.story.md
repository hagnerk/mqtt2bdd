# Story 2.5: Enhance Structured Logging for Operations

## Status

Approved

## Story

**As a** system operator,
**I want** comprehensive structured logs with consistent context fields,
**so that** I can troubleshoot issues and monitor application health.

## Acceptance Criteria

> ACs 1–8 and 11 are copied verbatim from Epic 2 in `docs/prd.md`. AC9 and AC10 are reworded to reflect two documented deviations (see Dev Notes → Deviation: AC9 payload truncation, and Dev Notes → Deviation: AC10 "JSON structure"). AC12 folds in a QA finding that gate 2.4 deferred to a follow-up story (see Dev Notes → Carry-Forward Findings).

1. All log entries include consistent context fields: `timestamp`, `level`, `message`, `component` (e.g., "mqtt", "database", "main")
2. MQTT events logged with context: `event` (connected/disconnected/subscribed), `broker`, `topic` (if applicable)
3. Database events logged with context: `event` (connected/disconnected/write_success/write_failure), `host`, `database`
4. Message processing logged with context: `topic`, `payload_size`, `duration_ms` (time to write)
5. Error logs include full error context: `error`, `component`, `operation` (what was being attempted)
6. Startup sequence logged showing initialization of each component
7. Log output includes application version injected via build-time ldflags (e.g., `-ldflags="-X main.Version=0.1.0"`), defaulting to "dev" for local development
8. All timestamps in ISO 8601 format with timezone (UTC)
9. Debug mode logs additional details: raw MQTT payloads **in full, untruncated**, SQL queries, connection pool stats (see Dev Notes → Deviation: AC9 payload truncation)
10. Manual test: Review logs in Docker logs output, verify structured field consistency (see Dev Notes → Deviation: AC10 "JSON structure")
11. All code passes `go fmt`, `go vet`, and `staticcheck`
12. **(FIND-015)** A message dropped at shutdown because the buffer was full is logged at WARN with its topic, so shutdown-time data loss is observable rather than silent

## Dev Notes

### Previous Story Insights (Stories 2.3.1 / 2.4)

- **Do not reintroduce a reconnection state machine in `dbWriterLoop`.** Story 2.3.1 deliberately *removed* `inReconnect`/`attempt` and the three log lines `"Database connection lost"`, `"Attempting database reconnection"`, `"Database reconnected successfully"`, because `InsertMessage` already logs `ERROR` on **every** failed attempt — the state machine added no diagnostic signal. `dbWriterLoop` and `insertWithRetry` must stay free of logging and of a `*slog.Logger` parameter. Enriching the *existing* `InsertMessage` log lines (this story) is the sanctioned way to improve write observability. [Source: docs/stories/2.3.1.story.md]
- **`msgChan` is never closed** — shutdown is signalled through a dedicated `done` channel. This is a load-bearing invariant (it is what makes "send on closed channel" impossible by construction, resolving FIND-014). Task 5 touches the `<-done` case of a `select` only; do not restructure the surrounding shutdown logic. [Source: docs/stories/2.4.story.md, cmd/mqtt2bdd/main.go:46-67, 112-125]
- The MQTT client already carries `shutdown`/`closeOnce` for a cancellable `reconnectLoop`; leave that mechanism alone. [Source: internal/mqtt/client.go:28-32, 89-95]

### Deviation: AC9 payload truncation — payloads are logged in full

AC9 as written in the epic says "raw MQTT payloads **(truncated)**". **The PO has explicitly ruled that payloads are logged whole**, with no truncation helper and no length cap.

**Rationale (PO decision, 2026-07-25):** a truncated payload is worth little for the job this log line exists to do. When a message fails to parse or lands in the database malformed, the diagnostic value is in the *end* of the payload as often as the start — a cap silently removes exactly the evidence being hunted. DEBUG is an opt-in level, enabled deliberately during an investigation, so the verbosity is bounded by the operator's own choice of `LOG_LEVEL`.

**Consequences the dev agent must respect:**

- The `logger` package gains **no** `TruncatePayload` (or equivalent) function, and **no** `maxDebugPayloadLen` constant. Do not reintroduce either "for safety".
- The Paho callback logs `"payload", string(msg.Payload())` verbatim. `payload_size` stays on the line — it remains the cheap field to filter and aggregate on.
- The level guard around the DEBUG call is **still required**, for a different reason than before (see Performance below).
- This is a deliberate divergence from the epic's wording, not an oversight. **QA should not raise it as a defect.** The PRD's AC9 is to be amended to match.

**Operational note:** at DEBUG, log volume now scales with payload size rather than being capped per message. This is accepted. If it ever becomes a problem in production, the fix is a dedicated payload-logging toggle, not a silent reinstatement of truncation.

### Deviation: AC10 "JSON structure" — the handler stays TextHandler

AC10 says "verify JSON structure". **The architecture mandates a text handler, not JSON**, in three separate places, and the codebase has shipped text output since story 1.4:

- "Structured Logging: Go 1.21+ `log/slog` with **text output**" [Source: docs/architecture/high-level-architecture.md:90]
- "`log/slog` with **Text handler** for human-readable output" [Source: docs/architecture/components.md:83]
- "Zero dependencies, **human-readable text output**" [Source: docs/architecture/tech-stack.md:23]

**Resolution: keep `slog.NewTextHandler`.** AC10 is satisfied as "review the Docker log output and verify structured-field consistency" — the intent of the AC (operator can read and correlate fields) is met by `key=value` output. Switching to `JSONHandler` would contradict three architecture documents and the stated rationale (human-readable logs for manual debugging) on the strength of one word in a PRD acceptance criterion. **Flagged for PO awareness** — if the PO wants genuine JSON output, that is an architecture change and warrants its own story, not a silent handler swap here.

### Deviation: `sensor` vs `topic` as the log attribute key

`internal/database/queries.go` currently logs the identifier under the key `"sensor"` (4 call sites). AC1 requires *consistent* context fields across components and AC4 explicitly names the field `topic`; the `mqtt` and `main` components already use `topic`, and the value is literally the MQTT topic string. Emitting the same value under two different keys is exactly the inconsistency AC1 targets.

**Resolution: the log attribute key becomes `topic` everywhere** — three sites carry `"sensor"` (`queries.go:31`, `:39`, `:44`) and a fourth carries `"truncated_sensor"` (`queries.go:19-22`), which becomes `"truncated_topic"`. The Go parameter (`sensor string`) and the SQL column (`sensor`) are unchanged — those name the database concept, the log field names the pipeline concept. Log message format is explicitly non-contractual, so this rename breaks nothing. [Source: docs/architecture/test-strategy-and-standards.md#what-not-to-test]

### Log Field Vocabulary (authoritative for this story)

Baseline fields on **every** entry — `time`, `level`, `msg` come from slog itself; `component` is attached once per component logger via `logger.WithComponent` / `.With(...)` (AC1):

| Field | Source | Values |
|-------|--------|--------|
| `time` | slog `TimeKey`, rewritten to UTC | ISO 8601 / RFC 3339 with `Z` suffix (AC8) |
| `level` | slog | `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `msg` | slog | short lowercase-ish phrase, no interpolated values |
| `component` | `.With()` at construction | `main`, `mqtt`, `database` |

Per-component **inherited** fields (attached once at construction, never repeated per call):

| Component | Inherited fields |
|-----------|------------------|
| `mqtt` | `broker` (AC2) |
| `database` | `host`, `database` (AC3) |
| `main` | — |

`event` vocabulary (one per log call; the enumerations in AC2/AC3 are the required subset, the rest are the states those components actually have):

| Component | `event` values |
|-----------|----------------|
| `main` | `starting`, `unknown_log_level`, `config_load_failed`, `config_loaded`, `buffer_initialised`, `writer_started`, `startup_complete`, `startup_aborted`, `buffer_full`, `message_dropped`, `shutdown_signal`, `flush_complete`, `flush_timeout`, `shutdown_complete` |
| `mqtt` | `connecting`, `connected`, `connect_timeout`, `connection_lost`, `reconnecting`, `reconnected`, `reconnect_cancelled`, `disconnected`, `subscribing`, `subscribed`, `message_received` |
| `database` | `connecting`, `connected`, `disconnected`, `write_success`, `write_failure`, `write_duplicate`, `topic_truncated`, `pool_stats` |

`operation` — **required on every ERROR or WARN entry that reports a failed *attempt*** (AC5), naming what was being attempted: `load_config`, `connect`, `reconnect`, `subscribe`, `parse_dsn`, `ping`, `insert`.

Entries that report a *state* rather than a failed attempt carry **no** `operation`, **whatever their level** — there is no operation to name. These are `connection_lost` at ERROR, and `buffer_full`, `message_dropped`, `flush_timeout`, `write_duplicate`, `topic_truncated`, `unknown_log_level` at WARN. `connection_lost` (`internal/mqtt/client.go:59`) is the single ERROR in that list and the reason this rule is not phrased "every ERROR carries an operation": the broker dropped the link on its own, no local call was attempted, so any `operation` value would be fabricated. Do not invent one to satisfy a blanket rule; AC5 is about error *context*, and a fabricated `operation` on a state entry is noise, not context.

Message-processing fields (AC4), on the `write_success` / `write_failure` / `write_duplicate` lines: `topic`, `payload_size` (bytes), `duration_ms` (`time.Since(start).Milliseconds()` around the `pool.Exec` call). `duration_ms` uses `Milliseconds()` following the pattern documented in the architecture. [Source: docs/architecture/error-handling-strategy.md#logging-standards-for-errors]

### Required Context Fields (architecture)

> **Required Context Fields:** `error` — error message string; `component` — package/module name (mqtt, database, main); `operation` — what was being attempted (insert, connect, subscribe); domain-specific context — sensor name, message ID, etc.
>
> **Log Levels:** DEBUG — retry attempts, transient errors; WARN — degraded state, duplicates, buffer high; ERROR — failed operations, connection failures; FATAL — unrecoverable errors (startup only).

[Source: docs/architecture/error-handling-strategy.md#logging-standards-for-errors]

The logger package has no FATAL level (slog has none); the project's equivalent is `Error(...)` followed by `os.Exit(1)`, which is what the startup paths already do. Do not invent a custom level.

### Security (non-negotiable)

- **Never log credentials, the DSN, or `cfg.PostgresPassword` / `cfg.MQTTPassword`** — not even at DEBUG. The `database.Client.dsn` field is documented "never logged" (`internal/database/client.go:24`); Task 2's `config_loaded` line must carry only `log_level` and `buffer_size`. This constraint (**SEC-001**, raised in gate 1.3) has been upheld and verified by QA in every story since. [Source: docs/qa/gates/1.3-implement-configuration-package.yml, docs/qa/gates/1.5-implement-mqtt-client-connection.yml, docs/qa/gates/1.7-implement-postgresql-client-connection.yml]
- The MQTT payload is sensor telemetry, not credentials — DEBUG-only payload logging was already accepted by QA in story 1.6. [Source: docs/qa/gates/1.6-implement-mqtt-subscription-and-message-reception.yml] Logging it **in full** (see the AC9 deviation above) does not change that assessment: the broker carries home-automation device readings, and the application subscribes to `#` without ever handling authentication material on the message path. The credentials ban above applies to `cfg.*Password` and the DSN, which never transit through a payload.

### Performance

The per-message DEBUG log in the Paho callback (Task 3) is on the hot path. `slog` evaluates its variadic arguments **before** checking the level, so `string(msg.Payload())` would copy the entire payload into a fresh allocation for every message received, even when running at INFO. Removing truncation makes this guard *more* important, not less: the copy is now proportional to the full payload rather than capped. Guard the call with `c.logger.Enabled(context.Background(), slog.LevelDebug)`.

The `duration_ms` timing in `InsertMessage` (Task 4) needs no guard — `time.Now()`/`time.Since` are cheap and negligible next to a database round-trip.
