# Story 2.2: Implement MQTT Automatic Reconnection

## Status

## Story

**As a** system operator,
**I want** the application to automatically reconnect to MQTT broker after connection loss,
**so that** the service recovers without manual intervention.

## Acceptance Criteria

1. `internal/mqtt/client.go` adds connection lost callback handler to MQTT client configuration
2. On connection lost, log ERROR with reason: "MQTT connection lost: <reason>"
3. Implement reconnection loop with fixed 10-second retry interval
4. Reconnection attempts logged at INFO level: "Attempting MQTT reconnection (attempt <n>)..."
5. On successful reconnection, log INFO: "MQTT reconnected successfully" and re-subscribe to topics
6. Reconnection runs in separate goroutine to avoid blocking main application
7. Reconnection loop continues indefinitely until connection is re-established
8. Application continues running during MQTT outage (doesn't crash or exit)
9. Manual test: Stop Mosquitto container, verify reconnection attempts logged every 10 seconds, restart Mosquitto, verify successful reconnection and message reception resumes
10. All code passes `go fmt`, `go vet`, and `staticcheck`

## Dev Notes

### Previous Story Insights (Story 2.1)

- The DB writer goroutine in `cmd/mqtt2bdd/main.go` already contains an inner retry loop that holds any failed message and retries every 10 seconds until the INSERT succeeds. This means **messages published to `msgChan` are never lost during a DB outage** — the channel buffer absorbs messages while MQTT is disconnected as well.
- During an MQTT outage the `msgChan` stops receiving new messages (MQTT handler is silent), but the DB writer continues draining whatever is in the buffer. This is correct and requires no change in this story.
- `opts.SetAutoReconnect(false)` was explicitly set in story 1.5/1.6 with the comment "will be implemented as a manual reconnection loop in story 2.2." That comment must be removed in this story; `SetAutoReconnect(false)` itself stays.

### Architecture: MQTT Reconnection Pattern

The reconnect approach uses Paho's `ConnectionLostHandler` to trigger a goroutine, not Paho's built-in auto-reconnect. This gives explicit control over attempt counting and logging. [Source: architecture/error-handling-strategy.md#runtime-errors-transient]

Expected log output during outage (slog TextHandler format — reason in structured `error` field, no `component` field per existing code pattern):
```
ERROR MQTT connection lost error="EOF"
INFO  Attempting MQTT reconnection attempt=1
ERROR MQTT reconnection failed attempt=1 error="connection refused"
INFO  Attempting MQTT reconnection attempt=2
...
INFO  MQTT reconnected successfully
INFO  subscribing to MQTT topic topic=#
INFO  MQTT subscribed topic=#
```

**AC2 note:** "MQTT connection lost: \<reason\>" in the AC refers to the reason being present in the log — it is satisfied by structured logging with a separate `"error"` field (not by embedding the reason in the message string). This matches the existing handler pattern in `client.go`.

Log fields to use (slog structured logging with `log/slog`):
- Connection lost: `l.Error("MQTT connection lost", "error", err)` — already present
- Reconnect attempt: `c.logger.Info("Attempting MQTT reconnection", "attempt", attempt)`
- Reconnect failure: `c.logger.Error("MQTT reconnection failed", "attempt", attempt, "error", err)`
- Reconnect success: `c.logger.Info("MQTT reconnected successfully")`

[Source: architecture/error-handling-strategy.md#logging-standards-for-errors]

### Architecture: Concurrency Rules

- Every goroutine must have a clear exit condition. [Source: architecture/coding-standards.md#concurrency]

- The `ConnectionLostHandler` is called by Paho in its own goroutine — launching another goroutine from within it is safe.

### Refactoring Performed

- **File**: `internal/mqtt/client.go`
  - **Change**: Replaced `l.Error(...)` with `c.logger.Error(...)` in the `ConnectionLostHandler` closure.
  - **Why**: The closure captured the constructor-local variable `l` while all other logging in the file uses `c.logger`. Both point to the same `*slog.Logger` at runtime, but the inconsistency is a latent maintenance hazard — if the logger field were ever updated, the closure would silently use a stale reference.
  - **How**: Now the closure consistently accesses the logger through the struct pointer, matching the pattern used in every other method.
