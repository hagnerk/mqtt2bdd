# Story 5.2: Repair Payload Content PostgreSQL Refuses

## Status

Ready for Review

## Story

**As an** operator,
**I want** payload content that PostgreSQL refuses but that can be repaired safely to be repaired rather than discarded,
**so that** a large, legitimate message such as `zigbee2mqtt/bridge/definitions` is stored instead of lost.

## Acceptance Criteria

> **ACs 1–8 are copied verbatim from Epic 5 in `docs/prd.md:913-931`.** None is reworded and none is added. Where an AC leaves a detail open, the answer is recorded in Dev Notes → SM Clarifications, with its source or its reasoning. Release target: **v1.0.1**, together with Story 5.1 (Done), which this story builds on.

1. `internal/database` repairs the payload before the checks of Story 5.1, replacing each defect with U+FFFD:
   - a JSON `\u0000` escape becomes `\uFFFD`, in keys and values alike, and only when its backslash starts an escape, meaning it is preceded by an even number of backslashes (zero included). `"\\u0000"` is literal text and stays untouched, while `"\\\u0000"` is repaired
   - an unpaired UTF-16 surrogate escape becomes `\uFFFD`: a high surrogate (`\uD800`–`\uDBFF`) not immediately followed by a low surrogate escape, or a low surrogate (`\uDC00`–`\uDFFF`) not immediately preceded by a high one. Valid pairs stay untouched, and hex digits are matched case-insensitively
   - each maximal invalid UTF-8 byte sequence (including CESU-8 encoded surrogates and overlong forms) becomes the UTF-8 encoding of U+FFFD
2. Nothing else is transformed. Escaped control characters `\u0001`–`\u001F`, noncharacters such as `\uFFFF`, and valid surrogate pairs are accepted by PostgreSQL and pass through byte-for-byte. Numeric overflow and structural errors are not repairable and remain rejected by Story 5.1
3. A payload needing no repair is returned unchanged without allocating, verified by a test using `testing.AllocsPerRun`
4. A repaired message is logged once at WARN with `event=payload_sanitized`, no `operation` (it reports a state, not a failed attempt), `topic`, `payload_size`, and one count per repair kind: `nul_escapes`, `lone_surrogates`, `invalid_utf8_sequences`
5. Unit tests cover every repairable case of the proposal's probe table, backslash runs of length 1 to 4 before `u0000`, an escape at the very end of the payload, several defects in one payload, and a payload containing none
6. An integration test publishes `{"a":"x\u0000y"}`, a lone surrogate and a raw `0xff` byte, and finds each stored with U+FFFD in place of the defect
7. The README states that stored JSON may differ from the published payload in this way, and that the database must use the `UTF8` encoding
8. Verification passes as in Story 5.1, AC12

## Dev Notes

### Context: why this story exists

v1.0.0 stalled in production on `zigbee2mqtt/bridge/definitions` (283 KB, retained): PostgreSQL refused it with SQLSTATE `22P05` because it contains a JSON `\u0000` escape, and the writer retried it forever. Story 5.1 (Done) stopped the stall: that message is now discarded and logged as `write_rejected`. This story turns that loss back into a stored row, by repairing the three families of content PostgreSQL refuses that can be repaired without guesswork. [Source: docs/sprint-change-proposals/2026-09-17-write-pipeline-stall.md#1-identified-issue-summary; docs/prd.md → Epic 5]

**Compatibility (Epic 5):** no schema change, no new Go dependency, and a valid payload is written exactly as today — a payload without defects is returned as the same slice, so the INSERT receives identical bytes. Rollback is `git revert` of this story alone; 5.1's rejection then takes over again. [Source: docs/prd.md → Epic 5 → Epic Context]

**Secondary risk (Epic 5):** stored JSON differs from what the device published. Mitigation: only content PostgreSQL would refuse is touched, always with the visible U+FFFD, and every repair is logged. `jsonb` never stored payloads byte-for-byte anyway. [Source: docs/prd.md → Epic 5 → Risk mitigation; docs/architecture/error-handling-strategy.md#3-runtime-errors---data-integrity-log-and-skip]

### What PostgreSQL refuses (probe, PostgreSQL 15.17, `pgx/v5` v5.7.2, `JSONB NOT NULL`, `server_encoding=UTF8`)

| Payload | `json.Valid` | PostgreSQL | This story |
|---------|--------------|------------|------------|
| `\u0000` escape (in a value or in a key) | true | **22P05** | Repaired → `\uFFFD` |
| `\\u0000` (escaped backslash, literal text) | true | OK | Untouched |
| Lone high `\ud83d`, lone low `\ude00`, reversed pair `\ude00\ud83d` | true | **22P02** | Repaired → `\uFFFD` each |
| Valid pair `\ud83d\ude00` | true | OK | Untouched |
| Noncharacter `\uFFFF`, escaped control `\u0001` | true | OK | Untouched |
| Raw invalid UTF-8 (`0xff`, CESU-8 `ED A0 BD`, overlong `C0 AF`) | **true** | **22021** | Repaired → `EF BF BD` per maximal run |
| Raw NUL byte, raw tab in a string, BOM, `NaN`, trailing comma, truncated JSON | false | 22021 / 22P02 | Untouched → still rejected (`invalid_json`, Story 5.1) |
| Number out of `numeric` range (`1e1000000`) | true | **22003** | Untouched → still rejected (`sqlstate=22003`, Story 5.1) |
| Nesting depth 100,000 | false | 54001 | Untouched → still rejected |

A raw NUL byte is a byte `< 0x80`, so the repair never touches it; `json.Valid` rejects it, as in Story 5.1. [Source: docs/sprint-change-proposals/2026-09-17-write-pipeline-stall.md#2-evidence--what-postgresql-actually-rejects]

### Repair Algorithm

Target flow of `InsertMessage` after this story (only the Step 2 line is new):

```
truncate sensor (unchanged)
len(metrics) == 0          → DEBUG write_skipped, return nil                       (Step 1, unchanged)
payloadSize := len(metrics)
metrics, n := sanitizePayload(metrics)
n.total() > 0              → WARN payload_sanitized (counts), continue with repaired bytes   (Step 2, new)
!json.Valid(metrics)       → write_rejected reason=invalid_json                    (Step 3, unchanged)
pool.Exec(..., metrics)    → rejected / write_failure / success                    (unchanged; payload_size = payloadSize)
```

[Source: docs/architecture/error-handling-strategy.md#3-runtime-errors---data-integrity-log-and-skip]

`sanitizePayload` — single left-to-right scan over the bytes, index `i`, output buffer `out` allocated lazily (nil until the first defect):

| At `payload[i]` | Condition | Action | Advance |
|-----------------|-----------|--------|---------|
| `\` | next byte is `u` and four hex digits follow (case-insensitive) → value `v` | see the three rows below | — |
| | `v == 0x0000` | emit `\uFFFD`, `nulEscapes++` | 6 |
| | `0xD800 <= v <= 0xDBFF` and bytes `i+6..i+11` are `\u` + four hex digits with value in `0xDC00..0xDFFF` | emit the 12 bytes unchanged (valid pair) | 12 |
| | `0xD800 <= v <= 0xDBFF` otherwise | emit `\uFFFD`, `loneSurrogates++` | 6 |
| | `0xDC00 <= v <= 0xDFFF` | emit `\uFFFD`, `loneSurrogates++` (a low preceded by a high was consumed by the pair row) | 6 |
| | any other `v` (includes `\u0001`–`\u001F`, `\uFFFF`) | emit unchanged | 6 |
| `\` | next byte exists, is ASCII, and the `\u`+hex rule above did not apply | emit both bytes unchanged (`\\`, `\"`, `\n`, a malformed `\u00` …) — this is what makes `\\u0000` literal text | 2 |
| `\` | last byte of the input, or next byte `>= 0x80` | emit `\` unchanged; the next byte, if any, is handled by the next iteration | 1 |
| byte `< 0x80` | — | emit unchanged | 1 |
| byte `>= 0x80` | `utf8.DecodeRune(payload[i:])` returns a size `> 1`, or a rune other than `RuneError` | emit the `size` bytes unchanged (a literal `EF BF BD` lands here: `RuneError` with size 3 is valid) | size |
| byte `>= 0x80` | `DecodeRune` returns `RuneError` with size 1 | keep advancing while the next position also decodes as `RuneError` size 1 (the maximal run); emit `EF BF BD` once, `invalidUTF8Sequences++` | run length |

Notes on the table:

- "Next byte is ASCII" in the two-byte escape row matters: `\` followed by a raw invalid byte must not swallow that byte, or the UTF-8 repair would miss it. Such a payload is invalid JSON anyway and is rejected at Step 3, but the transform must stay consistent.
- The run rule stops at any byte that decodes validly, including an ASCII byte. `ED A0 BD` and `C0 AF` are each one run, hence one `EF BF BD`. A run is repaired inside or outside a JSON string alike; outside a string the result is still invalid JSON and is rejected at Step 3.
- A truncated `\u` at the end (`\u`, `\u0`, `\u00`, `\u000`) fails the "four hex digits follow" test and falls into the two-byte row: unchanged. A high surrogate whose six following bytes are missing or are not a low surrogate escape is lone and repaired, including at the very end of the input.
- Every escape repair is length-preserving (6 → 6); only the UTF-8 repair changes the length (n → 3). That is why the output cannot be written into the input slice, and why a fresh buffer is needed once a defect is found. `make([]byte, 0, len(payload)+8)` then `append(out, payload[:i]...)` is sufficient; exact capacity is not specified.
- Lazy allocation: while `out == nil`, "emit unchanged" means nothing (the bytes are still in `payload`); at the first defect, `out = append(make(...), payload[:i]...)`; afterwards every emit appends to `out`. At the end, `out == nil` ⇒ return `payload`.

### SM Clarifications

Where the ACs leave a detail open, these answers apply.

- **C1 — "Maximal invalid UTF-8 byte sequence" means a maximal run of consecutive bytes that `utf8.DecodeRune` reports as invalid (`RuneError`, size 1).** A run becomes one U+FFFD and counts as one in `invalid_utf8_sequences`. This is the semantics of Go's `bytes.ToValidUTF8`, and it matches the AC's own examples: the CESU-8 surrogate `ED A0 BD` and the overlong `C0 AF` are each named as one sequence. Go's decoder already rejects surrogate code points and overlong forms, so no extra rule is needed. `bytes.ToValidUTF8` itself is not used: it does not return a count and allocates on every call.
- **C2 — "Logged once" means one entry per `InsertMessage` call, not one per defect** (decided by the maintainer, 2026-09-17). `insertWithRetry` calls `InsertMessage` again with the original payload after a transient failure, so a repaired message that meets a database outage logs `payload_sanitized` again on each attempt, next to each `write_failure`. The alternative — repairing once before the retry loop through a new exported method — was rejected: it changes the public API and `cmd/mqtt2bdd`, and a direct `InsertMessage` call would no longer repair. Task 5 records this in `error-handling-strategy.md` §3.
- **C3 — `sanitizePayload` is a byte transform, not a JSON parser.** It never fails and never validates; invalid JSON goes through it (with any invalid UTF-8 runs repaired) and is then rejected by Step 3, exactly as in Story 5.1. This also lets unit tests use short fragments such as `x\u0000` for "an escape at the very end of the payload" (AC5). A backslash only ever appears inside strings in valid JSON, so treating every `\` as an escape start is correct for every payload that can be stored.
- **C4 — `payload_size` is the received size, before repair, on every entry for the message.** `logging-standards.md` fixes it for `payload_sanitized`; applying it to the outcome entries too keeps all the entries of one message (and its DEBUG `message_received`) reporting the same size, so they can be correlated. The difference is at most two bytes per invalid byte and zero for escape repairs.
- **C5 — No counter and no health field for repairs.** No AC asks for one, and `rejected_last_interval` (5.1) already covers the loss side. A repaired message that is stored counts in `processed_last_interval` like any other.
- **C6 — File placement.** The architecture places the repair in `internal/database` without naming a file. `sanitize.go` keeps the byte-level transform apart from the query code in `queries.go`, following the existing one-concern-per-file split (`client.go`, `queries.go`). The function is unexported: `cmd/mqtt2bdd` never calls it. `docs/architecture/components.md` therefore needs no new interface entry.
- **C7 — AC6's "lone surrogate" and "raw `0xff` byte"** are each published inside a JSON string (`{"a":"x\ud83dy"}` and `{"a":"x<0xff>y"}`), so that after the repair the payload is valid JSON and is stored. A bare `0xff` payload would be repaired and then rejected as invalid JSON, which proves nothing about storage.
