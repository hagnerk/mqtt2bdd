# Story 4.3: Automate Cross-Platform Binary Builds on Tag

## Status

Ready for Review

## Story

**As a** maintainer,
**I want** a tagged version to automatically produce downloadable binaries for four platforms,
**so that** publishing a release is one `git push --tags` and never a manual build.

1. `.github/workflows/release.yml` exists, triggered only by pushed tags matching `v*.*.*`
   (including pre-release suffixes such as `v0.9.0-rc1`)
2. The workflow runs the project's existing quality gates in a first job that the build and
   publish jobs depend on, so no artefact is built and no release is created if any gate fails:
   - static analysis and unit tests: `gofmt -l .` (must report nothing), `go vet ./...`,
     `staticcheck ./...`, `go test ./...`
   - the integration suite: `./test/run-integration-tests.sh`, run from the repository root as
     documented. The script is already self-contained and CI-friendly from Story 3.3 — it brings
     the isolated `test/` stack up, waits for health, runs the `//go:build integration` suite,
     tears everything down unconditionally, and exits non-zero on any failure — so it needs no
     workflow-specific adaptation beyond a runner that provides Docker Compose
   These gates run on GitHub's runners, not on a contributor's machine: this is a publication
   gate, not a git hook. A failing gate leaves the pushed tag and commits in place and blocks
   only the release; recovering means fixing, deleting the tag locally and remotely, and
   re-tagging. The AC12 pre-release rehearsal exists so that this is never first discovered on
   `v1.0.0`
3. A build matrix produces one static binary per target: `linux/amd64`, `linux/arm64`,
   `linux/arm` (with `GOARM=7`, for 32-bit Raspberry Pi OS), and `darwin/arm64`
4. Every build uses `CGO_ENABLED=0` and `-ldflags="-s -w -X main.Version=<version>"`, where
   `<version>` is the tag with its leading `v` stripped (`v1.0.0` → `1.0.0`) — identical flags to
   the production `Dockerfile`, so a released binary matches a container-built one
5. Each target is packaged as a `.tar.gz` archive under a **canonical, version-bearing name**:
   `mqtt2bdd_<version>_linux_amd64.tar.gz`, `mqtt2bdd_<version>_linux_arm64.tar.gz`,
   `mqtt2bdd_<version>_linux_armv7.tar.gz`, `mqtt2bdd_<version>_darwin_arm64.tar.gz` — so that a
   downloaded file states on disk which version it holds
6. Each archive is **also** published under a version-free alias name
   (`mqtt2bdd_linux_amd64.tar.gz`, `mqtt2bdd_linux_arm64.tar.gz`, `mqtt2bdd_linux_armv7.tar.gz`,
   `mqtt2bdd_darwin_arm64.tar.gz`), byte-identical to its canonical counterpart. The alias exists
   solely to make the `releases/latest/download/<name>` URL resolvable — that URL requires an
   asset name that does not change between releases. A release therefore carries eight archives,
   four distinct payloads
7. Each archive contains the `mqtt2bdd` binary (executable bit set), `LICENSE`, and `README.md`
8. A `checksums.txt` asset lists the SHA-256 of all eight archives in the standard
   `sha256sum -c` input format. Each canonical/alias pair necessarily shares one checksum, since
   the payloads are identical; the file lists both names so that either download can be verified
   without knowing about the other
9. The workflow creates a GitHub Release on the tag, attaches the eight archives plus
   `checksums.txt`, and uses GitHub's auto-generated release notes as the body
10. A tag carrying a pre-release suffix (`-rc`, `-beta`) produces a release marked as
    pre-release, so it never becomes the target of the `latest` URL — the aliases it publishes
    are reachable only through its own pinned tag URL, which is the intent
11. The workflow declares `permissions: contents: write` and authenticates with the default
    `GITHUB_TOKEN` only — no additional secret is configured in the repository
12. The workflow is rehearsed end to end on a `v0.9.0-rc1` tag before `v1.0.0` is tagged: the
    run succeeds, all nine assets are present, a canonical and an alias archive verify to the
    same SHA-256, and the extracted `linux/amd64` binary runs and logs
    `event=starting version=0.9.0-rc1`
13. Workflow YAML is commented to the standard of the rest of the repository — each job and each
    non-obvious step (the `v`-stripping, `GOARM=7`, why each archive is published under two
    names) explains its rationale, consistent with this project's educational intent
14. **[Carry-forward, TEST-001]** `test/run-integration-tests.sh`'s failure path is independently
    exercised rather than accepted on the Dev's account: a deliberately broken scenario is
    introduced, the script is run, and it is confirmed to (a) exit **non-zero** and (b) still tear
    the stack down completely via its `trap cleanup EXIT`. Open since gate `3.3`, where AC9's
    negative path was accepted without being re-exercised; this story is the first to make that
    exit code load-bearing, because AC2 puts it in front of every release

- [x] Task 2 — Write the trigger, permissions and version extraction (AC: 1, 4, 11)
  - [x] `on: push: tags: ['v*.*.*']` and nothing else — no `workflow_dispatch`, no `push: branches`.
        AC1 says "triggered **only** by pushed tags". Note why the glob works for pre-releases:
        GitHub's tag filter treats `*` as matching any run of characters except `/`, so the final
        `*` in `v*.*.*` absorbs `0-rc1` and `v0.9.0-rc1` matches. This is non-obvious and is exactly
        the kind of thing AC13 wants commented.
  - [x] `permissions: contents: write` declared at workflow level (AC11). Nothing broader. This is
        the minimum that `gh release create` needs, and declaring it explicitly means the workflow
        does not silently inherit whatever the repository's default token permissions happen to be.
  - [x] No secret beyond the automatic `GITHUB_TOKEN` (AC11). Use `env: GH_TOKEN: ${{ github.token }}`
        for the `gh` CLI rather than configuring a PAT. State in a comment that no repository secret
        is required, so nobody adds one believing it is needed.
  - [x] Version extraction (AC4): `VERSION="${GITHUB_REF_NAME#v}"`. `GITHUB_REF_NAME` is the tag name
        for a tag push (`v1.0.0`), and `${VAR#v}` is POSIX prefix removal — it strips **one** leading
        `v` and leaves everything else, so `v0.9.0-rc1` → `0.9.0-rc1`. Comment why the `#v` form is
        used rather than a `sed`/`tr` deletion, which would also strip a `v` occurring elsewhere.
  - [x] Pre-release detection (AC10): a tag is a pre-release if the version contains a `-`. Semver
        defines everything after the first `-` as the pre-release identifier, so this test is exact
        rather than heuristic, and it covers `-rc`, `-beta`, `-alpha` and anything else without
        enumerating them.

  - [x] `GOARM: 7` on the `linux/arm` entry only (AC3). Comment why: `GOARCH=arm` alone defaults to

### Why the Alias Must Be a Copy, Not a Second Tar

This is the one decision in the workflow that looks like a shortcut and is actually a correctness
requirement, so it is stated once here and commented once in the YAML.

> **[Corrected during implementation — the premise below was empirically false, the conclusion was
> not.]** The draft asserted that gzip embeds an mtime, so two `tar -czf` runs a second apart would
> produce different bytes. **Measured: they do not.** Two `tar -czf` invocations two seconds apart
> over identical inputs produced identical SHA-256 sums on both GNU tar 1.35 / gzip 1.13 (the
> toolchain `ubuntu-latest` ships) and BusyBox tar. The mechanism the draft missed: gzip only writes
> an MTIME when it compresses a *named file*; when it compresses a stream — which is exactly what
> `tar -z` hands it — the MTIME field is written as 0. The corrected reasoning is below, and the
> shipped workflow comment states the corrected version, not this one.

AC6 requires each alias archive to be **byte-identical** to its canonical counterpart, and AC8
requires that "each canonical/alias pair necessarily shares one checksum".

A second `tar -czf` would, on today's toolchains, satisfy that — as measured above. **The decision to
use `cp` stands anyway, for a better reason than the draft gave: it turns a property that currently
holds by accident into one that holds by construction.** The byte-identity of a published pair would
otherwise depend on gzip's stream-vs-file MTIME behaviour, on directory read order, and on whatever
the runner image's `tar` does after its next update — none of which anyone would think to re-check
before cutting a release, and all of which a user's failed `sha256sum -c` would report first.

`cp` costs one line and removes the entire class of failure. The alternative — `gzip -n` or
`tar --mtime` with a fixed timestamp — would pin the timestamps but not the ordering, and would
still be a reproducibility argument rather than a guarantee.

The workflow's checksum step asserts the outcome (8 lines, 4 distinct hashes) so that a regression
here fails the release rather than reaching a user.

Task 8's local check (`sha256sum canonical alias` → two identical hashes) is what proves this, and
Task 6's assertion (8 lines, 4 distinct hashes in `checksums.txt`) is what would catch a regression
in CI.

### Correction to the Story's Own Reasoning (found during Task 8)

The story's Dev Notes section "Why the Alias Must Be a Copy, Not a Second Tar" asserted that gzip
embeds an mtime, so two `tar -czf` invocations a second apart would produce different bytes and
therefore different checksums.

**That is empirically false, and I measured it rather than assuming either way:**

| Toolchain | Two `tar -czf` runs, 2 s apart, identical inputs |
| --- | --- |
| BusyBox tar (the `go-dev` container) | **identical** SHA-256 |
| GNU tar 1.35 / gzip 1.13 (`debian:stable-slim`, the toolchain `ubuntu-latest` ships) | **identical** SHA-256 |

The mechanism the draft missed: gzip writes an MTIME only when compressing a **named file**. When it
compresses a **stream** — which is exactly what `tar -z` hands it — the MTIME field is written as 0.
So there was no non-determinism to work around in the first place.

**The `cp` decision still stands, on better grounds.** A second `tar` would work *today*, by an
accident of how gzip handles streams. `cp` makes AC6's byte-identity structural: independent of the
runner image's `tar` after its next update, of directory read order, and of anything a future edit to
that step introduces. The failure mode being avoided is not "the checksums differ today" but "the
checksums start differing at some point, in an artefact nobody re-checks before publishing, and the
first person to notice is a user whose `sha256sum -c` fails".

The shipped workflow comment states this corrected reasoning, not the draft's. The story's Dev Notes
section carries an inline correction block marked as such, rather than being quietly rewritten — the
wrong premise is part of the record of how the decision was reached.

### Note for Story 4.4

Two things found while verifying AC8 that Story 4.4 AC5 needs, since it must document the checksum
sequence:

1. **`sha256sum --ignore-missing -c checksums.txt` works on GNU coreutils (Linux) and on macOS**
   (both `sha256sum` and `shasum -a 256` accept it) — verified on both. So the command AC5 names is
   correct for every platform this project publishes a binary for.
2. **It does *not* work on BusyBox** (`sha256sum: unrecognized option: ignore-missing`), which is
   what Alpine ships. A user verifying a checksum inside an Alpine container would need
   `sha256sum -c` against a filtered `checksums.txt` instead. Marginal for the audience — a
   home-automation user is on Raspberry Pi OS, Debian, Ubuntu or macOS — but worth one line rather
   than a support question.
